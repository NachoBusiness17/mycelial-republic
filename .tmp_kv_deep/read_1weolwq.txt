Now here is the interesting part.  I discovered that the Nvidia driver on windows f\*\*\*s you over by default.  I am using 616.56 for CUDA 13.4 support.  You need to go to Graphics -> Program Settings -> Add a program, select your llama-server.exe, and then find "CUDA Memory Fallback" and set it to "Prefer no fallback".  if you do not do this, it will attempt to not allocate what your calling application requests, and instead shift some vram to windows shared memory (system ram) degrading performance.   With the combination of --load-mode node --fit off -ngl 99 and --kv-offload, it keeps all layers on gpu, all vram cache on gpu, and if it cant allocate, it fails and crashes with oom.  Doing this I have been able to push for a much larger kv cache.

I have a nice powershell command that I built a while back:

    Get-Counter "\GPU Process Memory(*)\Local Usage" | 
        Select-Object -ExpandProperty CounterSamples | 
        Where-Object { $_.CookedValue -gt 1MB -and $_.InstanceName -match "pid_(\d+)" } | 
        Select-Object @{Name="PID"; Expression={ [int]$Matches[1] }}, @{Name="VRAM_MiB"; Expression={ [math]::Round($_.CookedValue / 1MB, 2) }} | 
        Group-Object PID | 
        Select-Object @{Name="ProcessName"; Expression={ (Get-Process -Id $_.Name -ErrorAction SilentlyContinue).Name }}, 
                      @{Name="PID"; Expression={ $_.Name }}, 
                      @{Name="Total_VRAM_MiB"; Expression={ ($_.Group | Measure-Object VRAM_MiB -Sum).Sum }} | 
        Sort-Object Total_VRAM_MiB -Descending | 
        Format-Table -AutoSize

It shows the vram used per process, which is useful for tracking what is active or what can be gotten rid of.  I am literally allocating

 llama-server    14955.27MiB

and that is without adjusting the nvidia drivers, this was impossible as the token rate would not be maintained and would drop off as it would claim to allocate, but was actually shifting part of the workload to system memory.

--- Legal_Dimension_ (1): heres an extract from my Pi lessons learned - not sure if it will help or not  
  
3. Blackhole reads its config once per process. Changing pi-blackhole-config.json (e.g. setting "midRunCompaction": "resume") does nothing until you fully restart Pi. A running session

keeps the old settings and can climb from 158k to 192k tokens unchecked inside one tool loop.



 4. Your thresholds are mis-stacked, or something else calls ctx.compact().

\- contextWindow in models.json must leave room for output — prompt + generation share the window. Set it to (served context − max output), e.g. 176,000 for a 196k window with 16k max

output. Otherwise Pi thinks more prompt fits than actually does and you get stop=length truncation (one-token answers, cut-off tool-call JSON).

\- Never call bare ctx.compact() from an extension — it aborts the active run by design. If you have a custom compaction/context-guard extension, make it advisory-only and let blackhole

own compaction.

\- Stack your thresholds so each fires before the next: advisory % < compactAfterTokens (e.g. 140k) < Pi's backstop (contextWindow − reserveTokens) < hard prompt ceiling.

\- Also check the practical prefill ceiling: if your server can't prefill the context inside the client timeout (measure tok/s under a prefill workload, not generation), you'll die

before compaction ever fires — a "dead band".
