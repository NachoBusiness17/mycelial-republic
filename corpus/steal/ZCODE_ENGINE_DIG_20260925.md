Date: 2026-09-25. Follow-up to the 09-24 ten-lane survey (corpus/steal/ZCODE_REPO_STEAL_MAP_20260924.md), covering the three subsystems that pass named as under-read: the dynamic-workflow engine (which we run on and pay tokens to), core's context-compaction strategy, and the hook/permission contract our security hooks must honor.

## engine-internals

**What it is.** The dynamic-workflow engine is a deterministic, zero-I/O state machine that executes agent workflow scripts. A script is typechecked against a facade, lowered into `__host.*` calls, and run in a sandboxed child process; every host call (ask / world-read / report / artifact) is journaled under a `(siteId, ordinal)` key so a resumed run short-circuits finished work from the journal and re-runs only the unfinished tail. Amend-resume adds a second, subagent-name-keyed cache imported from a predecessor run, gated by a write-closes-purity rule.

**Architecture.** Two packages. `dynamic-workflow` (pure, no node builtins) holds the engine; `dynamic-workflow-runtime` holds the process harness.

Execution identity: every facade call site mints ordinals at one point (`nextOrdinal`, engine.ts:685); instance = `siteId@ordinal`. The journal (`JournalStorePort`, engine/types.ts:878; in-memory impl journal-memory.ts:31) has three tables: run row, node rows keyed `siteId@ordinal` (kinds ask/world-read/world-run/report/artifact, types.ts:429), and an append-only event log. Every event goes through one funnel that journals + emits (`record`, engine.ts:711).

Replay/cache matching: on every host call the engine consults its own journal first. An ask hit on `completed`/`failed` short-circuits with no driver call — failed rows replay as rejections so scripted try/catch branching replays identically (scheduler.ts:128-160, 363-382); a `running` row is re-dispatched live (crash recovery). The defensive inputHash is FNV-1a 32-bit over canonical JSON (sorted keys, undefined skipped — hash.ts:12-50); for asks it covers only the instruction string, computed at admission (scheduler.ts:125). Any mismatch fails the whole run with structured `InputHashMismatch {expected, got}` (scheduler-types.ts:135). At a second level, resume itself is refused unless the recorded sha256 script hash matches (`ScriptHashMismatch`, engine.ts:336-348; hash computed in bootstrap/dynamic-workflow-run-submit.ts:630). Resume restores settle order, report count, artifact versions, tokens, and import-closure state from the journal + events (engine.ts:352-383).

Settle-order replay: ordinals minted after an `await` depend on wall-clock completion order, so replay releases cached settles in the *first-born settlement order* recovered from the run's own events — first `node-settled`/`artifact-*` per claimable instance (ask/world nodes and content artifacts; not reports or sync preset declarations) — with a one-microtask delivery delay so awaits attach in order (replay-order.ts:51-83, 141-189). The gate permanently opens at run settlement so no promise dangles (replay-order.ts:92).

Subagent-name → cache mapping (amend-resume): the run service builds a pure `ImportedRunCache` from the predecessor journal (bootstrap/dynamic-workflow-import.ts), keyed by effective actor name; the engine matches at runtime: non-empty name (duplicates fail the run, `DuplicateActorName`, engine.ts:416-437) plus canonical-JSON persona equality, else the candidate is dropped (imported-cache.ts:212-223). Per actor, `entries[seq]` is matched by inputHash; miss ⇒ monotone divergence — never re-consulted — which cascades for free because new upstream results change downstream instruction hashes (imported-cache.ts:44-79). A per-hash world queue with an occurrence cursor matches the n-th `{op,args}` occurrence to the n-th record (imported-cache.ts:183-198). The gate closes on the FIRST WRITE: driver-reported `askMutating` before a mutating tool, or a live world-run (engine-world.ts:104, 173-188); after closure only pure asks (`stats.worldToolCalls === 0`; missing stats counts as touched) still hit (`takeIfPure`, imported-cache.ts:70-79). An in-flight predecessor ask can be *continued* rather than replayed if five conditions hold (not diverged, seq==entries.length, prefix consumed, hash match, gate still open); the new session is seeded with the predecessor's transcript prefix and inherited model pin (imported-cache.ts:136-176). Divergence state is re-derived per recorded seq on crash-resume via `reconcileRecorded` using live/queued-before-close sets recovered from event order (imported-cache.ts:101-123; engine-world.ts:203-218).

Scheduling: per-actor FIFO, one in-flight ask per actor, global `activeAsks` cap read live from mutable caps; `setMaxConcurrency` swaps the caps object, persists, and pumps on increase (scheduler.ts:394-403; engine.ts:579-591). Recorded asks are admitted in actorSeq order before fresh ones (scheduler-types.ts:167-185). Typed asks get submit_result validation with REPAIR_ATTEMPTS=3 (types.ts:941) and one nudge on turn-end-without-submit (NUDGE_ATTEMPTS=1, types.ts:944); exhausted budgets become node-level `ValidationFailed`/`ResultNotSubmitted` (scheduler-submit.ts:23-116). A lenient single JSON.parse rescues string-encoded payloads and reports post-parse violations (scheduler-submit.ts:70-92).

Errors/retry: taxonomy in engine/errors.ts:41-76 — node-level codes reject one catchable promise (ValidationFailed, ResultNotSubmitted, DriverError, Cancelled, ContextLimit, WorldReadCapExceeded, content-artifact family); run-level codes fail the run (InputHashMismatch, UnknownActor, MissingAskSpec, DuplicateActorName, ReportCapExceeded, preset-artifact family) — the split is by *rejection channel* (void ops have nowhere to reject), not severity; construction-time ScriptHashMismatch; host-level Interrupted (process died) and ProviderStop (deterministic model-side error ⇒ `stopRun` ⇒ `stopped(provider)`, resumable). Transient model failures never surface: the driver redrives with 2s→60s jittered backoff (Retry-After first), unbounded (bootstrap/workflow-driver-model-failure.ts:81-125; workflow-driver-helpers.ts:219-226).

ContextLimit/compaction: compaction runs inside each ask's runtime turn loop (core/runtime/methods/turn-loop.ts:83, reason ContextLimit; reactive on provider overflow). If compaction itself fails, the shared policy table rules `context_exceeded` and the driver fails just that node with catchable `ContextLimit` — no retry (workflow-driver-model-failure.ts:56-67; adapters/src/model/workflow-model-failure-policy.ts:96-97).

Escalation/questions: never crosses the engine. A subagent's `escalate` tool is driver-side: `escalation-raised` event (engine/types.ts:664-686; no node row — waiting is not work), the ask parks on a deferred tool result, and the run service resolves it via `respondToParkedEscalation` → `escalation-resolved`, the answer becomes the tool result (bootstrap/workflow-driver-escalation.ts:50-80). Budget: MAX_ESCALATIONS_PER_ASK=3; exhaustion returns a normal tool result telling the model to proceed (workflow-driver-helpers.ts:84-90).

Compiler pipeline: `compileWorkflowScript`/`createWorkflowProgram` wrap the script in `async function __workflowScript__()`, typecheck-only against the facade .d.ts + embedded ES2022 libs in a fully virtual in-memory host (compile.ts:31-55, 135-164). strict on; `noUncheckedIndexedAccess` deliberately off (TS2532 was 96% of undefined-family failures, compile.ts:44-49); `types: []` so `process`/`fetch` fail to compile — the purity contract starts here. `lowerWorkflowScript` = compile + facade-misuse + site collection + lowering (lower.ts:94-104); dirty scripts are never lowered. Bootstrap's run-submit compiles once: synthesizeAskSchemas → buildAskSpecs → lowered body + author text + sha256 (dynamic-workflow-run-submit.ts:595-630); askSpecs must cover every ask site or the run dies with `MissingAskSpec` rather than silently degrade typed→untyped (engine.ts:464-476).

Runtime: harness spawns `node --max-old-space-size=256 <entry>` where the entry is a self-contained ESM file written to `<cwd>/.zcode/workflow-runs/<runId>.mjs` (Windows 32,767-char argv limit; ELECTRON_RUN_AS_NODE=1 forced; harness.ts:182, 250-276). NDJSON over stdio; the child is a vm context with only ES intrinsics + `__host`; runtime bans Date.now/argless Date/Math.random (child-source.ts:227-247). Failure normalization: script throw ⇒ errored; crash/timeout/protocol corruption ⇒ stopped(interrupted), resumable; abort reason maps to stopped user/model/interrupted/superseded (harness.ts:350-446).

**Steals.**
- **Journal-first replay with per-site ordinals + hash tripwire** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/scheduler.ts`) - Every host call checks `(siteId, ordinal)` in the journal before doing work: completed results short-circuit with zero driver calls, failed results replay their exact rejection, and a 32-bit FNV-1a over canonical JSON of the input loudly fails the run on any divergence instead of silently drifting. Cheap (one map lookup) and turns resume into pure prefix reuse.
- **Settlement-order gate reconstructed from the event log** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/replay-order.ts`) - Ordinals minted after an await depend on wall-clock completion order, so naive replay dead-locks on its own hash checks. Holding cached settles until their first-born settlement order (recovered from first `node-settled` events, one-microtask FIFO delivery) makes replay bit-exact with zero schema migration.
- **Name+persona runtime cache identity with monotone divergence** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/imported-cache.ts`) - Amend-cache hits are matched at runtime by effective actor name + canonical-JSON persona, per-actor seq-aligned entries; any hash miss flips a one-way `diverged` bit and invalidates the rest for free via downstream hash changes. Combined with 'gate closes on first write, only pure asks survive' it keeps caching honest about workspace mutation.
- **Error taxonomy split by rejection channel** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/errors.ts`) - Node-level vs run-level codes are decided by whether the operation returns a promise the script can catch — void ops (report, preset artifacts) fail the run because there is nowhere to reject. Stable string codes plus structured mismatch/providerStop payloads mean flow logic never matches error text.
- **One policy table shared by runner retry gate and driver stop boundary** (`zcode-repo/apps/zcode-cli/packages/adapters/src/model/workflow-model-failure-policy.ts`) - The same `resolveWorkflowModelFailurePolicy` decides both whether the retry loop may re-send a model request and whether the driver stops the run — so the runner can never retry its way past something the driver would treat as permanent. Workflow traffic gets an unbounded retry budget with only human-fixable errors (auth/quota/config) stopping the run.

**Operator notes (we run on this).**
- Cache hits demand byte-identical instruction text: the hash is FNV-1a over the instruction string only, so ANY wording change to an ask invalidates it and everything downstream that interpolates its result (hash.ts:48, imported-cache.ts:51). Edit instructions surgically.
- The first workspace write closes the amend-cache for the whole run; after that only tool-free asks (worldToolCalls===0) still hit. Front-load read-only research asks before any mutating ask or world.run if you want amend-resume to pay off — the naive 'any live ask closes the gate' design measurably lost 6 of 50 fanout hits (scheduler.ts:233-237).
- Resuming a failed run replays the failure, not a retry: failed asks are journaled and re-rejected deterministically (scheduler.ts:371-381). To actually re-run a failed ask you must amend into a new run, not resume.
- ProviderStop runs (auth/quota/model-not-found/invalid-request) are stopped but resumable — fix the credential or quota and resume; everything settled in the journal is free on resume, and a run's reported spend includes all predecessors (engine.ts:114-122, 362).
- A run that looks hung is probably in transient backoff: model-side transient errors retry forever at 2s→60s and never surface, so watch for `run-stalled`/`node-waiting` events rather than assuming a dead run (workflow-driver-model-failure.ts:81-125).

## compaction-context

**What it is.** The core package's compaction-context subsystem is how the ZCode agent survives sessions longer than one model window. It is three layered defenses: eager tool-result truncation at execution time (bytes caps + on-disk artifacts), an opt-in microcompact that blanks old tool results in place without a model call, and full model-written compaction in three flavors (auto at a token threshold, manual /compact, reactive after a provider overflow) that replaces history with a 9-section summary plus a small verbatim tail. Session resume reconstructs provider context from the persisted transcript by replaying everything after the last compaction boundary, re-inserting the preserved tail segment, and re-injecting recently-read files and persisted system-reminders.

**Architecture.** TOKEN ACCOUNTING. There is no tokenizer. Estimate = ceil(chars/3) with CJK chars double-weighted (ESTIMATED_TOKEN_CHAR_DIVISOR=3, packages/shared/src/usage-stats.ts:9; context/utils.ts:8-15). estimateMessageTokens counts visible text, reasoning blocks, AND assistant toolCall inputs as JSON (compact/manual.ts:102-138). The estimate is only a fallback: the primary signal is the latest committed assistant's provider usage — tokenCount = providerBase(input or contextUsage) + locally-estimated delta of messages after that anchor (buildProviderUsageTokenOverride, runtime/methods/compact.ts:313-340; anchor scan in turn-model-step-usage.ts:54-64). A per-request preflight also caps maxOutputTokens to window − estimatedUsage − 1000 (model-token-limits.ts:34-40); default output budget is 32K (model-token-limits.ts:5). Context-usage snapshots with per-category breakdown (system prompt, meta-user, skills, tool schemas, messages) are logged per request (context-usage.ts:119-253).

ORDERING. Every model step in the turn loop runs: drain pending runtime commands → microcompactIfNeeded → rapid-refill check → autoCompactIfNeeded → rebuild tools/per-request reminders → provider projection with cache control → request (turn-loop.ts:55-213). Reminders regenerated each step: plan_mode_exit, runtime_mode, todo_reminder (persisted), output_style (step 0 only) (turn-loop.ts:120-167). Reactive compact additionally fires when the provider rejects the request as over-context (turn-model-step.ts:774 → methods/compact.ts:352-462).

AUTO-COMPACT POLICY (compact/policy.ts:6-14). Default window 200,000; effective input window = window − min(outputReserve, window) where outputReserve = min(modelMaxOutput ?? 32,000, 21,000); threshold = effective − 13,000 buffer → ~166,000 tokens default. Guards: compact requires ≥2 assistant-started rounds with ≥1 assistant message (manual.ts:69-75); circuit breaker stops auto-compact after 3 consecutive failures (MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3, policy.ts:138-144); a rapid-refill breaker blocks auto-compact that re-triggers within 3 tool turns of the last compact, and after 3 consecutive refills throws CompactRapidRefillError (RAPID_REFILL_TOOL_TURN_THRESHOLD=3 / MAX_CONSECUTIVE_RAPID_REFILLS=3, turn-loop-state.ts:21-22, 154-168).

KEPT vs SUMMARIZED vs DROPPED (runtime/helpers/compact-selection.ts). Entries split into a context prefix (system messages plus prefix attachments context_prefix/skills_listing, detected by metadata source or literal `<system-reminder>` text — lines 337-349) that is NEVER summarized, plus assistant-started rounds. Auto and Reactive triggers preserve the newest 1 round verbatim; Manual /compact summarizes everything except the prefix (shouldPreserveRecent, lines 36, 225). Summary request = whole history + a 9-section prompt (Primary Request / Key Concepts / Files & Code / Errors & fixes / Problem Solving / All user messages / Pending / Current Work / Next Step, compact/prompt.ts:14-109) with user custom instructions appended; summary output capped at min(model max, 20,000) tokens (compact-active.ts:716-725). The summary request runs tool-free if >100 tools are registered (COMPACT_TOOL_KEEP_MAX_COUNT=100, compact-active.ts:72-73, 251-257) so huge MCP schemas can't blow it. Auto trigger gets 3 attempts (AUTO_COMPACT_MAX_ATTEMPTS=3); on overflow the ladder is: re-select with MORE groups preserved — sized by parsing the token gap out of the provider error text `/N tokens > M/` (compact-selection.ts:229-266, 370-410) — then, for manual/reactive only, drop oldest rounds (20% of groups or gap-sized) with a `[earlier conversation truncated for compaction retry]` marker (compact-selection.ts:279-335); 3 retries max (manual.ts:55).

POST-COMPACT HISTORY (compact-active.ts:495-631, helpers/compact.ts:72-88). New history = prefix + summary-as-synthetic-user-message + preserved segment + plan-file reference + read-state reminders. Read-state re-injection replays recently-Read files as synthetic Read results: max 5 files, 5,000 est-tokens each, 50,000 total, .git paths excluded, files whose Read calls survive in the preserved segment skipped, oversized files reduced to a pointer note (compact-post-reminders.ts:20-51). readFileState is then cleared so stale read-tracking can't suppress future re-reads (compact-active.ts:625). Boundary payload records pre/post/truePost token counts and willRetriggerNextTurn = truePost ≥ threshold (compact-active.ts:549-573). Persistence is atomic with best-effort rollback of summary + reminder messages, and interrupted compact timelines are reconciled to Completed/Interrupted on resume (compact-persistence.ts:289-382, 200-279).

MICROCOMPACT (compact/microcompact.ts). Opt-in: runtime requires config.compact.microcompact.enabled === true (methods/microcompact.ts:105-116). Triggers: session idle > 60 min (time-based) or estimate ≥ threshold = min(0.9 × autoThreshold, autoThreshold − 2000) ≈ 149,400 default (lines 14-18, 77-81, 171-195). It rewrites tool results of Read/Bash/Grep/Glob/WebFetch/WebSearch/Edit/Write/ApplyPatch to the literal string `[Old tool result content cleared]`, keeping the most recent 5 tool-result groups; error results and image/video/file blocks are protected; no-op unless it saves ≥256 tokens (lines 12-29, 123-156, 224-256).

TOOL-RESULT TRUNCATION (first line of defense, before any compact). Default tool resultBudget: 100,000 bytes inline and for the model, head preview, strategy truncate, with suffix `[Tool output truncated by resultBudget: ...]` (tool/executor/result-serialization.ts:21-28, 201). Bash: 30,000 bytes inline (bash.ts:70), up to 5 GiB persisted to an artifact with a 2,000-char `<persisted-output>` preview pointing at the file path (bash.ts:71, tool/result-persistence-format.ts:5, 29-42). Read: 2,000 default lines, 25,000 est-token output cap, 256 KB file cap, partial reads target 85% of budget and end with an offset pointer (contracts/src/tools/read.ts:15-18; tool/handlers/read-text.ts:18, 123, 184-186).

SYSTEM-REMINDER MECHANICS (system-reminder/source.ts). Three lifecycle classes: 2 request-prefix sources (context_prefix, skills_listing — part of the never-summarized prefix), 15 persisted sources (todo_reminder, resume_referenced_session_context, rewind_notice, …), and 10 per-request sources regenerated each model step (runtime_mode, hook_context, date_change, …) (lines 20-51). Bodies are wrapped in `<system-reminder>` tags with nested tags HTML-escaped, and a set of sources is eligible for mid-conversation-system delivery (lines 76-86, 203-237).

SESSION RESUME (runtime/methods/resume.ts:100-219; agent/session-history-hydrator.ts). Resume rebuilds provider history from the persisted transcript: take the active branch up to the LAST compaction boundary part, then re-insert the boundary's preservedSegment (head/tail message IDs) right after its anchor; assistant token baselines in the preserved segment are invalidated so they can't anchor usage estimates (agent/compact-session.ts:4-58). Persisted synthetic reminders restore as attachment entries per their source descriptor; text attachments restore as prompt_attachment reminders; tool calls that never finished become the synthetic error `[Tool execution was interrupted before resume]` (session-history-hydrator.ts:45, 149-190, 426-463). readFileState is rehydrated before context init (resume.ts:137-146). Cross-session context reuse (ReadSessionContext tool) is a separate scored-snippet transcript formatter: 24,000-char default budget (max 48,000), lite strategy ≤5 chunks of 28,000 chars (session-context/read-session-context.ts:16-20, 376-379).

**Steals.**
- **Provider-usage anchored token counting** (`apps/zcode-cli/packages/core/src/runtime/methods/compact.ts:313-340`) - Instead of trusting a chars/3 estimator for the compact decision, it takes the last committed assistant's real provider input/contextUsage as a base and only estimates the message delta since that anchor. This kills the classic failure where local estimates drift 20%+ on tool-heavy history, while still working across providers that don't return usage.
- **Trigger-differentiated preserve policy** (`apps/zcode-cli/packages/core/src/runtime/helpers/compact-selection.ts:36`) - Auto/reactive compaction keeps the newest assistant round verbatim (so in-flight work continues seamlessly), while manual /compact summarizes everything. One selection function, one boolean, and the summary quality/risk tradeoff is explicit per trigger instead of a global magic number.
- **Token-gap-driven retry sizing** (`apps/zcode-cli/packages/core/src/runtime/helpers/compact-selection.ts:370-410`) - When the summary request itself overflows, it regex-parses the provider's 'N tokens > M' error to compute exactly how much to shed, then preserves/drops just enough assistant rounds to cover the gap — with a bounded 20%-per-drop fallback and a truncation marker injected so the model knows history is elided.
- **Bounded read-state replay after compaction** (`apps/zcode-cli/packages/core/src/runtime/helpers/compact-post-reminders.ts:8-51`) - After compacting away file contents, it re-injects up to 5 recently-Read files as synthetic Read-tool-result reminders under hard budgets (5K tokens/file, 50K total), downgrading oversized files to a 'use Read' pointer. Recovers working-set continuity after compaction without reopening an unbounded context hole.
- **Rapid-refill thrash breaker** (`apps/zcode-cli/packages/core/src/runtime/methods/turn-loop-state.ts:154-168`) - Detects the compact→giant-tool-output→compact loop: if context re-crosses threshold within 3 tool turns of a compact, 3 consecutive occurrences block auto-compact and fail the turn loudly. Turns a silent token-burning loop into a diagnosable error with counters in the log context.

**Operator notes (we run on this).**
- The real auto-compact cliff is ~166K tokens on a 200K-window model (200K − 21K output reserve − 13K buffer, compact/policy.ts:6-14); the model's declared maxOutputTokens lowers the reserve, so switching to a small-output model moves compaction earlier.
- Microcompact is opt-in, not default: unless config.compact.microcompact.enabled is true, tool results only shrink at the 166K full-compact cliff. Turning it on gives a ~149K pre-stage that blanks old tool outputs for ~free (no model call).
- Bash output is capped at 30KB inline with full output persisted to a 5GiB-cap artifact file; huge outputs land on disk, not in context — but long-lived hosts accumulate these artifacts and need cleanup.
- Manual /compact preserves NOTHING verbatim except the system prefix — no recent-turn tail, unlike auto-compact's 1 preserved round. Run /compact only at a natural boundary, or you lose the working tail; the summary prompt's transcriptPath pointer is the only way back.
- Compaction thrash (compact → huge tool output → compact again within 3 tool turns, 3 times) fails the turn with CompactRapidRefillError; look for `compact.rapid_refill_breaker` in logs and find the tool emitting enormous output rather than retrying.

## hooks-permissions

**What it is.** The tool-gating contract of the zcode-cli agent: a sequential hook runner (7 lifecycle events incl. PreToolUse/PermissionRequest/PostToolUse) layered in front of a PermissionService (allow/ask/deny) plus an async permission broker that asks the human client. Hook verdicts can hard-block a tool call, mutate its input (with a mandatory re-permission), or just inject additional context into the model's transcript. Project ('workspace') hooks are additionally gated by a digest-pinned trust/admission layer that fails closed; everything — including MCP tools — funnels through the same executeToolCall pipeline.

**Architecture.** All paths below are under apps/zcode-cli unless noted.

EVENTS & SCHEMA. Seven hook events — SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Stop — defined in packages/contracts/src/hooks/index.ts:7-15, with the HookJSONOutput zod schema at :208-286 (continue, decision approve|block, additionalContext, event-specific hookSpecificOutput; PreToolUse carries permissionDecision allow|ask|deny + permissionDecisionReason + updatedInput; PermissionRequest carries decision {behavior: allow|deny|ask, message, updatedInput, permissionUpdates}).

RUNNER. core/src/hooks/runner.ts (InMemoryHookRunner): hooks run sequentially in registration order (line 82); matching = event + matcher where matcher omitted/'*' matches all, 'a|b' is literal alternation, otherwise RegExp (core/src/hooks/output.ts:98-112). Tool match values include aliases Agent<->Task and ApplyPatch<->Write/Edit (core/src/tool/compat.ts:6-10). Each hook is wrapped in a timeout — hook.timeoutMs ?? 60_000 default (runner.ts:42,340) — abort-linked to the turn signal (core/src/hooks/runner-helpers.ts:50-64). Per-hook try/catch (runner.ts:211-248): throw/timeout/cancel emits a HookRunFailed event (outcome failed|timed_out|cancelled, runner-helpers.ts:78-83) and continues — a failing hook never blocks. Output interpretation is output.ts processHookOutput: continue:false => blockRequested (and preventContinuation on PreToolUse/PermissionRequest/UserPromptSubmit, :154-160, and deny on permission events); decision:'block' => block; hookSpecificOutput with wrong hookEventName throws and voids the hook (output.ts:53-61). Merging across hooks is conservative: deny > ask > allow (output.ts:145-152).

COMMAND HOOKS. core/src/hooks/configured-runner.ts builds registrations from user config and workspace snapshots. The callback (core/src/hooks/configured-runner-callback.ts) spawns via the ExecutionPort — mode 'shell' or 'argv' (:26-115) — with cwd, env overlay of CLAUDE_*/ZCODE_* PROJECT_DIR/SESSION_ID (+ plugin root/data) (core/src/hooks/configured-runner-input.ts:74-98) and ${VAR} expansion that hard-errors on SKILL_DIR (input.ts:120-137). **Steals.**
- **Race-the-responders permission ask** (`apps/zcode-cli/packages/core/src/tool/executor/permission-responder-race.ts`) - The human-approval broker and the PermissionRequest hook chain start concurrently; the broker's answer deferred is registered synchronously so the visible approval window is never dead, first decision wins, the loser is aborted only after the winner settles (a hung loser can't block the winner), and a crashed hook chain forfeits instead of deciding for the user.
- **Exit-code-2 as the universal blocker** (`apps/zcode-cli/packages/core/src/hooks/configured-runner-callback.ts`) - A third-party PreToolUse blocker needs exactly one behavior: exit 2 and stderr becomes the deny reason shown to the model; exit 0 with valid JSON gives finer control (allow/ask/deny/updatedInput); exit 0 with junk or any other exit code is a logged no-op/failure, not a block. Crisp, testable contract.
- **Fail-open hook crash semantics with classified lifecycle events** (`apps/zcode-cli/packages/core/src/hooks/runner.ts`) - Every hook runs under a per-hook timeout (default 60s) and a try/catch that emits HookRunFailed with outcome failed|timed_out|cancelled and continues the chain — a broken security hook degrades to observability, never to a silent veto or a hung turn, and the block/no-block distinction lives only in explicit verdicts.
- **Re-verify authorization at every dispatch boundary** (`apps/zcode-cli/packages/core/src/hooks/workspace-hook-runtime-admission.ts`) - Admission for each workspace hook is re-evaluated immediately before every dispatch with a per-workspace security revision (epoch+counter) — revocations, policy tightening and trust-store reloads take effect for hooks that haven't started yet, and trust-store corruption fails closed with a distinct reason code.
- **Re-permission after any input rewrite** (`apps/zcode-cli/packages/core/src/tool/executor/permission-input-recheck.ts`) - Both PreToolUse updatedInput and PermissionRequest hook modify results are re-normalized, re-validated against the schema, and pushed through PermissionService again before execution — a hook or approver can't launder a denied path (or memory-file write) through an edited input.
