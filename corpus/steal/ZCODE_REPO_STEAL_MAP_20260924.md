# zai-org/ZCode - full-repo steal map

Date: 2026-09-24. Under survey: shallow clone of https://github.com/zai-org/ZCode at commit `29628c9acdb81b703bbd4080c207a0e7ce5e276e`.
Corpus: 664,533 lines of TypeScript across 3,208 .ts files (plus 765 .tsx), 7,090 files, 124 MB. pnpm monorepo: 13 packages under packages/ plus 17 under apps/zcode-cli/packages/.
Method: ten lanes cut on real package boundaries, one architect-subagent per lane reading the load-bearing files; every cited path existence-checked by an independent fact-checker.

## core-loop

**What it is.** The agent heart of the ZCode CLI: a deterministic AgentRuntime that runs the conversation loop (model request → tool calls → tool results → repeat), owns a tool registry + scheduler, gates every side effect through a permission ladder with human approval, keeps context under the model's window via micro/auto/reactive compaction, spawns full child AgentRuntimes for subagents, and assembles system prompts plus typed system-reminder injections. The model is just one port the engine calls; the engine owns truth.

**Architecture.** Entry point is AgentRuntime (zcode-repo/apps/zcode-cli/packages/core/src/runtime/agent-runtime.ts:132): the class body holds only state plus beginShutdown; ~60 methods are grafted on by installAgentRuntimeMethods (src/runtime/methods/index.ts), which assigns plain functions taking `this: AgentRuntimeInternal` onto the prototype.

Turn admission: executeTurn (src/runtime/methods/turn.ts:70) does not run inline — it enqueues a typed PromptRuntimeCommand (priority now/next/later, src/runtime/command-queue.ts) into a per-runtime serialized command queue, so prompts, task notifications, and subagent messages interleave in one ordered stream. executeTurnCommand (turn.ts:93) then freezes the admitted model selection before any await, runs SessionStart/UserPromptSubmit hooks (a hook can veto the prompt), persists the user message, and enters runRegularTurnLoop (src/runtime/methods/turn-loop.ts:43) — the actual agent heart: a while(true) that each round runs microcompactIfNeeded, autoCompactIfNeeded (a 'rapid refill' breaker can abort the turn), initializes MCP, projects the tool list (denylist filtering for automation/off-peak turns), commits system-reminder attachments (plan-mode-exit, runtime mode, todo, output style), builds the provider request with cache-control via buildRuntimeProviderRequestMessages, and calls runModelBackedTurnStep.

Model call: runModelTextRequest (src/runtime/methods/model.ts:36) is the only place the main loop invokes the model — model.streamText(modelRequest) at model.ts:228 (generateText fallback when streaming is off). Model objects are built by deps.modelFactory; provider adapters live outside core in packages/adapters (not opened). The stream is normalized into text/reasoning/toolCalls, tool_call ids are deduped, tool calls can start executing during the stream via a coordinator, and finishReason is classified: output-token-limit triggers a continuation request, context-exceeded triggers reactive compact, empty results get forensics before erroring.

Tool dispatch and results: extracted tool calls go to executeToolCallsForModelStep (src/runtime/methods/turn-tools.ts:43): each call gets a persisted pending tool part, then scheduleTools (src/runtime/methods/tools.ts:38) feeds registry metadata (readOnly/destructive/concurrentSafe/sideEffectScope) into ToolScheduler (src/tool/scheduler.ts) which topologically sorts and groups into parallel batches (max 10). executeSchedule (src/tool/executor/batch-runner.ts:56) runs each group via Promise.all, yields batch_start events, and cancels remaining tools if a result carries turnControl.stopTurnAfterResult. The per-call pipeline is executeToolCall (src/tool/executor/call-runner.ts:65): registry lookup → abort check → schema validation → entry.resolveInput normalization (deliberately before hooks, so hooks, permission rules, the confirmation payload, and the handler all see the same bytes) → PreToolUse hooks (deny/modify) → resolveToolPermission → ToolCallStarted event → handler under a pausable ToolDeadline → output validation → serialization with result budgets → PostToolUse hooks → result event → background-task tracking. Results flow back through three channels: a tool-result entry appended to the loop's provider-visible request history (turn-tools.ts:359), a persisted part with completed/error state for the session store (turn-tools.ts:302), and a workspace file-mutation checkpoint per mutating result (turn-tools.ts:370).

Permission: PermissionService.checkPermission (src/permission/service.ts:97) is an explicit ordered ladder — plan-mode transitions, requiresUserInteraction, alwaysAsk (structurally un-overridable, service.ts:131), yolo bypass, disallowed tools, project deny/ask/allow rules with per-tool rule policies, plan mode, webfetch/workflow-draft preapprovals, then mode-specific edit/build checks. 'ask' becomes a PermissionRequest emitted to a PermissionBroker; broker and PermissionRequest hooks race concurrently (racePermissionResponders, src/tool/executor/permission-flow.ts:184) because the old serial await killed confirmation windows; approved 'modify' inputs are re-normalized and permission-rechecked; approved rules persist to project rules or session-only grants.

Context management: four compaction mechanisms plus a circuit breaker. Microcompact (src/compact/microcompact.ts) blanks old tool-result contents ('[Old tool result content cleared]', keep 5 recent) at ~90% of the compact threshold. autoCompactIfNeeded (src/runtime/methods/compact.ts:184) runs pre-request each loop round using shouldAutoCompact with a token estimate overridden by the last committed assistant's real provider usage (buildProviderUsageTokenOverride, compact.ts:313). reactiveCompactAfterContextExceeded (compact.ts:352) fires when the provider itself returns context-overflow. /compact is a manual maintenance turn (compact.ts:45). All paths route through compactActiveConversation, which runs a separate summary model request (20K budget, src/runtime/methods/compact-active.ts) and persists a CompactCompleted timeline event; consecutive auto-compact failures are counted (autoCompactConsecutiveFailures, agent-runtime.ts:203). The breaker: evaluateRapidRefill (src/runtime/methods/turn-loop-state.ts:154) trips after 3 consecutive compacts with fewer than 3 tool turns between them, converting a compact loop into a typed error.

Subagents: SubagentPort (src/subagent/runner.ts:131) manages profiles, foreground/background lifecycle, a runtime-task registry, and completion notifications into the parent command queue. The child is a full second AgentRuntime constructed in runExploreAgent (src/runtime/methods/subagent.ts:239) with a pinned ModelSelection resolved override > profile > parent-inherit, a child model factory locked to that selection, an Explore-specific read-only PermissionService (or inherited parent service), mirrored tool events back to parent sinks, and a gate that the child session is durably persisted before SubagentSpawned is published (subagent.ts:376).

Prompt/reminder assembly: ContextBuilder (src/context/builder.ts:39) composes typed sections (identity, env, memory, skills, date) tagged with injectionTarget (system/meta_user) and cacheHint (stable/dynamic) into cache-anchored system messages. Runtime reminders are a closed enum of sources with channel/lifecycle/visibility descriptors (src/system-reminder/source.ts:88); wrapSystemReminder (source.ts:203) HTML-escapes nested <system-reminder> tags so model content can't forge one. MessageHistory (src/agent/message-history.ts:135) keeps message vs attachment entries with source metadata, and separates canonical history from the turn-scoped turnRequestState.entries array that the loop mutates and commits.

Persistence: everything durable flows through appendEvent (src/runtime/methods/events.ts:81) — eventStore.append assigns the sequence number, then durable persist, usage recording, and sink notification, in that order, so live/replay/snapshot all share one ordering truth. Not opened: tool handlers' internals (bash.ts, edit.ts, webfetch*.ts), browser-client, mcp/index.ts, hooks/runner.ts internals, steering/session-fork/rewind methods, packages/adapters.

**Steals.**
- **Pausable tool deadline** (`zcode-repo/apps/zcode-cli/packages/core/src/tool/executor/call-runner.ts`) - The tool timeout is a ToolDeadline whose clock pauses while nested model requests inside the handler wait at admission gates — the pause is wired by intercepting ModelNetworkStatus session events at the event outlet (observeToolAdmissionClock, call-runner.ts:355-363), so the handler never knows. This separates 'tool is slow' from 'the platform is congested' without coupling the two. _Estate use:_ Any estate tool that internally spawns model calls (verifiers, summarizers) should suspend its wall-clock budget while the inner call queues, instead of timing out on admission congestion.
- **Normalize before every gate** (`zcode-repo/apps/zcode-cli/packages/core/src/tool/executor/call-runner.ts`) - entry.resolveInput converts the model's raw args into 'the execution that will actually happen' before hooks, permission rules, confirmation payload, and handler run — the code comment states the goal outright: the policy sees the real script, versions agree, and confirmation and execution are the same bytes (call-runner.ts:204-231). Permission-modified inputs are re-normalized, re-validated, and permission-rechecked (permission-flow.ts:240-266). _Estate use:_ Estate approval gates should recompute over the exact post-normalization payload the handler will receive; anything the model wrote loosely must be normalized before the human sees it.
- **Race permission responders** (`zcode-repo/apps/zcode-cli/packages/core/src/tool/executor/permission-flow.ts`) - The permission broker and the PermissionRequest hook chain run concurrently; the first decision wins and the loser is aborted and never awaited (permission-flow.ts:177-236). The comment documents the production bug this fixed: serial hooks left a rendered confirmation window with no registered deferred, so every user click was silently dropped. Hook-chain failures explicitly forfeit rather than deny. _Estate use:_ Where an estate has both an interactive approver and automated approval hooks, race them with a forfeiting loser instead of sequencing — a hung hook must never brick a confirmation.
- **Rapid-refill breaker for compaction** (`zcode-repo/apps/zcode-cli/packages/core/src/runtime/methods/turn-loop-state.ts`) - Compaction loops are contained by a pre-stated numeric bar: 3 consecutive compacts with fewer than 3 tool turns between them trips a typed CompactRapidRefill error naming both thresholds (turn-loop-state.ts:154-168, thrown in turn-model-step.ts:742-771 and turn-loop.ts:91-98). Auto-compact failures are also counted on the runtime. Pure meters-not-prose: the unhealthy condition is detected by a counter with a published trip point, not prose heuristics. _Estate use:_ Any estate subsystem with a retry loop (compaction, checkpointing, escalation) should carry a numeric consecutive-attempts breaker that a bounded counter of healthy operations resets.
- **Persist-before-spawn gate for subagents** (`zcode-repo/apps/zcode-cli/packages/core/src/runtime/methods/subagent.ts`) - A child session must be durably persisted before the SubagentSpawned event is published (subagent.ts:370-382); the comment notes concurrent spawns used to race directory queries and lose children. Likewise a failed metadata write de-registers the runtime task so the parent never waits on a ghost (subagent/runner.ts:191-197). _Estate use:_ Estate fan-outs should make 'durable before announced' an admission gate, so downstream registries and projections can never enumerate a child that will never run.
- **Store-assigned sequence as the single ordering truth** (`zcode-repo/apps/zcode-cli/packages/core/src/runtime/methods/events.ts`) - Live event sinks receive only post-append events (events.ts:81-109): the comment explains that live sinks used to see sequenceNumber=0 while replay saw store-assigned numbers, creating two orderings for one session. Now append → durable persist → usage → sinks in that order, and everything (projection, resume, usage accounting) reads the same sequenced stream. _Estate use:_ Estate journals should let the store, not the writer, assign order, and show live observers only post-commit entries — one ordering fact for every consumer.

**Convergence with the estate.**
- engine-owns-truth: the model only narrates — tool calls are extracted, schema-validated, permission-gated, topologically scheduled by the runtime (turn-model-step.ts → turn-tools.ts → scheduler.ts), and a hallucinated tool call after a limit is dropped, never executed (turn-model-step.ts:455)
- append-only records: all durable state flows through appendEvent → eventStore.append with store-assigned sequence numbers (events.ts:81-147); compaction, rewind, and fork are new events over the log, never edits of old ones
- meters-not-prose: compaction is a pre-stated numeric bar (shouldAutoCompact threshold + provider-usage override), microcompact fires at 0.9×threshold−2000 tokens with a 256-token min-savings floor (microcompact.ts:16-18), and the rapid-refill breaker trips at exactly 3 consecutive compacts within <3 tool turns (turn-loop-state.ts:21-22) — unhealthy context is fixed by the system's own write patterns plus numeric breakers
- subagent fan-outs pinned to a named model with typed results: child runtimes get a pinned ModelSelection + locked model factory (subagent.ts:186-204) and return typed AgentOutput/ExploreSubagentRuntimeResult contracts, matching the estate law exactly
- Picasso law respected: package.json (packages/core/package.json:33-46) depends only on workspace contracts plus cheerio/diff/yaml/meriyah — no agent framework imported; the whole loop, scheduler, and permission ladder are rebuilt from first shapes
- hash-sealed manifests: partial convergence — versioned permission rulesets ({version:1}, service.ts:89) and content-typed workspace checkpoint artifacts, but I did not find content hashing on these collections; the estate's hash-seal law beats what core does here

## adapters

**What it is.** `@zcode/adapters` is the single ports-and-adapters package of the zcode-cli app (202 source files, 20 subpath exports per package.json: ./storage, ./fs, ./exec, ./http, ./image, ./pdf, ./provider, ./model, ./skills, ./plugins, ./auth, ./browser, ./mcp, ./mailbox, ./workflow, etc.). It implements the port interfaces defined in `@zcode/contracts` over Node built-ins (node:sqlite, fs, child_process, crypto), the Vercel AI SDK, and the MCP client SDK: model/provider execution, MCP connections, bash/exec process control, SQLite session persistence, skills/plugins/mailbox loaders, and image/pdf/media normalization.

**Architecture.** All ports live in `@zcode/contracts` (and `JournalStorePort` in `@zcode/dynamic-workflow`); this package implements them over Node built-ins plus Vercel AI SDK (ai@6) and `@modelcontextprotocol/client`. From the files I opened:

PROVIDERS: `src/model/model.ts` defines the local `ModelExecutor` port and `ExecutableModel`, which freezes capability properties/optionSpecs per model and validates every request (tools/images/PDF/video/JSON-schema) before the executor runs (model.ts:155-185). In `src/model/runner.ts`, `AiSdkModelAdapter.createModel` (runner.ts:138) takes a `RegistryProviderConfig` from the registry package at `zcode-repo/packages/provider` (outside this lane; I read `packages/provider/src/registry.ts` — a revision-numbered frozen-view registry with change listeners and model-selection validation) and calls `bindModel()`, which snapshots provider facts (endpoint, headers, apiKey) once so later registry hot-reload can never silently retarget a live model (model-execution.ts:170-194). Provider swap is a single switch on `api.type`: anthropic-messages→createAnthropic, openai-responses→createOpenAI, openai-chat-completions→createOpenAICompatible (model-execution.ts:363-372). The outbound fetch is a decorator stack: official Coding-Plan gateway rewrite → proxy-aware fetch shared with MCP so egress rules can't drift (model-execution.ts:505-509) → provider-business-error detection in JSON bodies and HTTP-200 SSE frames → TLS failure normalization → option-map rewriting → per-protocol compat fetches. Account (off-peak) models re-resolve auth per attempt via a refreshRuntimeHeadersBeforeAttempt port (runner.ts:160-190).

MCP: `src/mcp/index.ts` (1950 lines) implements McpPort over stdio (custom ProcessTreeStdioClientTransport owning the child tree), SSE and StreamableHTTP, a full OAuth stack (PKCE, credential store, token lease, refresh, interactive browser flow, oauth-*.ts), and official-server auth with a trusted-origins registry that fails closed. `src/mcp/pool.ts` is a lease-based connection pool: connection key = serverName + isolation scope (session vs workspace) + stable-stringified config (pool.ts:441-453); refcounted leases, idle-grace close timers, and on-demand ping revalidation that reconnects in place without breaking other lease holders (pool.ts:111-160).

SESSION PERSISTENCE: `src/storage/session-store/sqlite-session-store.ts` implements SessionStorePort on node:sqlite DatabaseSync, composed of per-aggregate repository modules (sessions, messages, session-entries, todos, usage, input-history, session-inputs, local-settings, script-workflow-*) plus `dwf-journal.ts`, the dynamic-workflow engine's durable journal — it imports the domain package type-only so the port stays in the domain and storage cannot perturb engine replay (dwf-journal.ts:1-11). Migrations are an ordered SQL array (migrations.ts:9-928) run inside `begin immediate` by `migration-runner.ts`, which records each migration's SQL checksum in schema_migration and verifies it on every startup, enforces WAL, retries SQLITE_BUSY with exponential backoff, and emits phased progress events for the UI (migration-runner.ts:99-231). Fork bundles are validated child-local before commit (sqlite-session-store.ts:115-150).

EXEC: NodeExecutionAdapter (thin shell over base/lifecycle/process/results/run modules) implements ExecutionPort with inline/persisted output budgets keyed by session+toolCall. Process-tree kill: POSIX process-group SIGTERM→SIGKILL with a ps-based descendant walk (exec/process-tree.ts); Windows adds taskkill plus Job Objects loaded via koffi FFI with KILL_ON_JOB_CLOSE so orphaned grandchildren die too (mcp/windows-job-object.ts:27-66).

LOADERS: `skills/scan.ts` shares one scan rule in sync+async variants with a documented error contract (only ENOENT swallowed; EACCES propagates) and a trust boundary: plugin-scope scans never follow symlinks — refuse, don't inspect (scan.ts:17-23). `plugins/` loads manifests, hooks, and plugin MCP server defs, installing from zip/GitHub-archive marketplaces via atomic directory swap. `mailbox/index.ts` is a filesystem unread/read mailbox where drain = read + atomic rename, with session-id pattern and path-escape guards. Extras: SSRF-guarded public-egress DNS filtering (http/public-egress-policy.ts:26-119), AES-256-GCM credential cipher keyed from an env secret (auth/credential-cipher.ts), env-driven fs fault injection for e2e (storage/fs-fault-injection.ts), a hook-trust store whose file lock records pid+token+process-start-time to survive PID reuse (storage/workspace-hook-trust-store.ts:28-59), and numeric image budgets with base64/token estimation (image/image-budget.ts).

NOT OPENED (named, not guessed): pdf/index.ts, logging/*, config/*, browser/*, the exec bash-* modules, auth OAuth flows in depth, plugins/marketplace.ts (2724 lines, only its index read), mcp/index.ts beyond the first 130 lines, repositories/sessions.ts, dwf-journal-introspection.ts, and most of the ~60 src/model/runner-*.ts fragments.

**Steals.**
- **Checksum-sealed migration ledger** (`zcode-repo/apps/zcode-cli/packages/adapters/src/storage/session-store/migration-runner.ts`) - Each migration's SQL is hashed and recorded in schema_migration alongside its id; on every startup applied rows are re-verified against the checksum and any divergence is a hard error. Dev-phase migrations were squashed into one immutable baseline with an explicit 'append-only after beta' rule in the 0019 comment. This is exactly claims-register thinking applied to schema history. _Estate use:_ Any estate-owned SQLite/JSON store should seal its ledger rows the same way: content-address each entry at write time, verify the whole chain on startup, append-only thereafter.
- **Lease-based MCP connection pool with config-hash keys** (`zcode-repo/apps/zcode-cli/packages/adapters/src/mcp/pool.ts`) - Connections are pooled under a key of serverName + isolation scope + stableStringify(config), leased with refcounts, closed after an idle grace, and ping-revalidated on demand — a stale connection reconnects in place so other lease holders never see a break. The pool also fixes the 'settings page shows connected forever' failure mode by probing before trusting a cached entry. _Estate use:_ The estate's per-session MCP/plugin processes could reuse this: lease = capability grant, config-hash key = automatic restart on config change, ping-revalidate = cheap liveness meters.
- **Frozen model binding snapshot** (`zcode-repo/apps/zcode-cli/packages/adapters/src/model/model-execution.ts`) - bindModel() captures provider endpoint/protocol/headers/apiKey into an immutable snapshot at model-creation time; the comment states the invariant: registry hot-reload must not silently switch a live model's endpoint, SDK factory, or auth. Request-time auth refresh is a separate, explicitly-typed port (refreshRuntimeHeadersBeforeAttempt) used only by account-backed models. _Estate use:_ When the estate swaps models per lane, bind the provider facts at fan-out time and re-resolve auth per attempt — config reloads then can't corrupt in-flight runs.
- **Refuse-don't-inspect symlink policy for untrusted scopes** (`zcode-repo/apps/zcode-cli/packages/adapters/src/skills/scan.ts`) - The file documents why realpath containment failed (the boundary leaked through every file-touch point) and collapses to one rule: plugin-scope scans reject symlinks at all three granularities — root, subdirectory, SKILL.md — because 'refusing needs no judgment about where the link points'. User-level roots keep symlink-following as a supported feature. _Estate use:_ The estate's skills/plugins directories are the same trust tier: reject symlinks at scan time instead of trying to chase and validate their targets.
- **Durable input admission ledger** (`zcode-repo/apps/zcode-cli/packages/adapters/src/storage/session-store/migrations.ts`) - Migrations 0016-0018 build session_input as a ledger where every queued input is durably admitted (admitted → promoted/cancelled/discarded/failed) with status_reason; the comment states the goal: 'queue vanished but never entered history' must be impossible, and crash cannot silently drop an input. The failed terminal state exists because fork children can fail after the parent already accepted the fact. _Estate use:_ Queued user prompts or inter-agent messages in the estate deserve the same ledger: admit durably first, then transition through explicit terminal states so nothing disappears without a trace.
- **SSE-frame business-error interception inside HTTP 200** (`zcode-repo/apps/zcode-cli/packages/adapters/src/model/model-execution.ts`) - Some OpenAI-compatible providers report business errors (quota, safety codes like 3007) only as error frames inside a 200 event-stream; a TransformStream parses each complete SSE frame, converts failures into a typed ProviderBusinessError preserving Retry-After headers, and drains the body within a bounded timeout so connection pools don't exhaust. Non-OK JSON responses get the same detection without trusting Content-Type. _Estate use:_ Any estate lane that streams from an LLM API should own its fetch layer this way: protocol-normalized typed failures with preserved headers beat string-matching provider prose downstream.

**Convergence with the estate.**

## bootstrap-cli

**What it is.** The CLI binary and its composition root. packages/cli is the executable (bin: zcode -> dist/zcode.cjs): main.ts sanitizes the process, run.ts dispatches commands (tui, headless -p, app-server/agent-server protocol servers, plugins/skills/doctor). packages/bootstrap is the composition root: create-app.ts wires ~15 ports into core's AgentRuntime per session, zcode-protocol implements the legacy v1 NDJSON JSON-RPC server over stdio, and zcode-protocol-v4 implements the newer conversation channel (topic pub-sub with projections, idempotent command admission, chunked attachments) living side by side on the same pipe. Everything is esbuild-bundled into one CJS file, optionally a Node single-executable binary.

**Architecture.** Boot chain. `cli/src/main.ts` is the process entry: it sets the process title, sanitizes env (proxy/cert vars are quarantined so they only revive inside Bash tool subprocesses), and installs stderr/console boundaries BEFORE any business import — because in protocol/TUI modes stdout is a strict frame channel and one stray console.log from any dependency would crash the transport (main.ts:30-35). It then dynamic-imports `run.ts`. `cli/src/run.ts` is the dispatcher: special early exits that must precede parseArgs (`__internal-search`, plugin-host, dwf sandbox child which is a self re-exec of this same binary — run.ts:303-307), then a command switch: `tui` (default), `app-server`/`agent-server` (protocol server), `-p/--prompt`, `--target` (rewritten to a `/goal` prompt), doctor/login/plugins/skills. Heavy code is reached through two lazy loaders: `bootstrap-loader.ts` (one shared promise importing `@zcode/bootstrap`) and `tui-runtime-loader.ts`.

Two routes into bootstrap. (1) In-process: headless prompt (`prompt-command.ts:166-167`) and the TUI (`tui-prompt-handler.ts:63`) call `createZCodeApp` directly — TUI and headless never spawn the protocol server. (2) Served: `app-server`/`agent-server` call `runZCodeProtocolAgent` (`zcode-protocol-entrypoint.ts`), which stages startup resources in order (SQLite migration first, then process-level provider-registry runtime, telemetry, MCP connection pool with per-session leases), each through `acquireProtocolStartupResource` with a `StartupTimer` emitting named start/complete/fail events, then builds `ZCodeProtocolAgentServer` + `ZCodeProtocolNdjsonConnection` (transport.ts) and tears everything down via `cleanupProtocolRuntime`.

The two protocol dirs answer the ask directly. `bootstrap/src/zcode-protocol/` implements the legacy v1 wire: NDJSON JSON-RPC framing (transport.ts: serialized request queue with a control-plane bypass so stop/cancel jump a stuck model turn, transport.ts:224-233; deterministic post-response outbox so a subscribe's initial frames are written after its ACK, transport.ts:235-260), `server.ts` dispatch (~60 legacy `zcodeProtocolMethods.*` cases: session/*, plugins/*, workflows/*, workspace/*), plus a session residency pool and resource sampler. `bootstrap/src/zcode-protocol-v4/` is the new conversation channel riding the same pipe: `v4-gateway.ts` (3454 lines) keeps per-session `ConversationTopicPublisher`s (bounded delta log + logEpoch + subscribe(base) adjudication + per-subscriber filter→coalesce→frame pipeline, conversation-topic-publisher.ts:1-12), a `CommandInbox` for command admission, and read APIs (row pagination, attachment begin/chunk/commit transaction, workflow-run artifact reads). ## protocol-spine

**What it is.** This lane is the wire between ZCode's UI, host/server and CLI core: a from-scratch VS Code-style IPC framework (@zcode/rpc), a zod-schema'd pub/sub protocol v4 (@zcode/shared/zcode-protocol-v4) that streams conversation/session state to desktop and web frontends, a thin renderer connection kit (@zcode/client) that turns channels into typed service proxies, and @zcode/contracts — the 21.5K-LOC hexagonal port layer of the CLI agent core (session event store, event reducer, dynamic-workflow run ports, tool contracts). Together they implement one idea twice at two scales: append-only events owned by an engine, folded by pure reducers into projections, delivered over a layered transport where every byte budget is a named constant.

**Architecture.** Three distinct layers, wired bottom-up:

1. `@zcode/rpc` (packages/rpc/src, 16 files, 3,295 lines) — a from-scratch re-implementation of VS Code's IPC stack, layered exactly as its index header documents (packages/rpc/src/index.ts:1-29): L0 Emitter/Disposable/CancellationToken/VSBuffer; L1 binary serialization with 1-byte type tags + VQL varints, JSON fallback for objects, and a base64 marker (`__zcode_rpc_nested_uint8array_v1`) so nested Uint8Arrays survive (packages/rpc/src/serialization.ts:136-235); L2 `IMessagePassingProtocol` (send/onMessage) implemented by SocketProtocol (13-byte header type/id/ack/length, ChunkStream peek-before-consume framing to survive TCP fragmentation — packages/rpc/src/protocol.ts:85-307) and MessagePortProtocol (with a flow-control sideband object rejected unless byte-exact, protocol.ts:41-58); L3 ChannelServer/ChannelClient — four request verbs (Promise, PromiseCancel, EventListen, EventDispose), header = [type,id,channelName,name], cancellation by disposing the CancellationTokenSource, and pending-request buffering so early RPCs wait for `registerChannel` instead of erroring (packages/rpc/src/channelServer.ts:38-41, 229-273); L4 IPCServer/IPCClient 1:N routing; L5 ProxyChannel.fromService/toService — any object becomes a channel (methods→call, `on*`→listen, `onDynamic*`→listen(arg), events pre-buffered so pre-subscribe emissions aren't lost — packages/rpc/src/proxy-channel.ts:46-97,178-213); L6 remote WebSocket reconnect that swaps the socket and replays unacked messages (`replaceSocket`, packages/rpc/src/remote.ts:295-320). PersistentProtocol (packages/rpc/src/persistent-protocol.ts) adds ACK + 5s keepalive + 20s ack timeout, a bounded replay buffer (8 MiB / 45 s; overflow = abandon session, client recovers via `subscribe(base)`), and hysteresis flow control (1 MiB high / 256 KiB low watermark → onSaturated/onDrained edges). Decorator middleware (logging-middleware.ts, network-telemetry-middleware.ts) wraps channels without touching the core.

2. `@zcode/shared` → `./zcode-protocol-v4` (10,868 lines of the 41K-line shared package) — the UI↔host↔CLI wire contract, zod schemas + pure functions only (its file-head discipline: no runtime/IO ever enters this package, zcode-protocol-v4/index.ts:1-5). Topic pub/sub: `hello`/`clientHello` handshake with capability bits and two delivery profiles — `continuous` (30 ms flush, all stream paths) vs `replayable` (150 ms flush, no tool-progress) (core.ts:26-59); subscribe carries a base watermark `{logEpoch, seq}`, the ACK-only response defers the initial snapshot/resume to a post-response owned notification (transport.ts:440-447); frames are `{fromSeq,toSeq, payload: snapshot|deltas}` over three topics (conversation/, sessions-index/, workspace-config/). Physical wire: logical frames >1 MiB fragment at UTF-8 byte level with crc32 checksums (wire.ts:18-43); validation is two-phase — a route-boundary 'candidate' schema checks only routing fields, full schema + typed faults run inside a bounded assembler state machine after ownership filtering (wire.ts:45-83, wire-assembler.ts). ~35 JSON-RPC methods (V4_METHODS, transport.ts:332-384) where read queries are deliberately stateless/timeout-resend-safe; attachments go through a begin/chunk/commit/abort transaction with 512 KiB chunks and a required sha256 (transport.ts:832-952). Deltas are a closed op set (delta.ts:96-140) with coalesce.ts guaranteeing merged application is byte-identical to per-delta application; workflow-runs-reducer.ts is the single reducer shared by the desktop projection and the TUI mirror (apps/zcode-cli/packages/tui/src/app-workflow-mirror.ts imports it). The live host side lives outside this lane in apps/zcode-cli/packages/bootstrap/src/zcode-protocol/ (server.ts imports V4_METHODS from shared; a v3 protocol server of ~257 leftover exports coexists in packages/shared/src/zcode-protocol with a written deletion boundary).

3. `@zcode/client` (733 lines) — renderer connection kit: WebSocket→ISocket adapter (websocket.ts:23-60), MessagePort connections with explicit dispose lifecycle (messageport.ts:25-49), and RemoteServiceAccess, which converts ~40 named service channels into typed ES6-Proxy service objects via ProxyChannel.toService, one getter per service (remoteServiceAccess.ts:96-222; the secret-writing provisioning target is deliberately made non-enumerable so it never shows on the accessor, lines 162-167).

4. `@zcode/contracts` (apps/zcode-cli/packages/contracts, 113 files, 21,540 lines) — the CLI agent core's port layer: 31 `*.port.ts` interfaces (session manager/store/sink/projection + EventReducerPort in interfaces/session.port.ts:57-225; dynamic-workflow-run.port.ts plus roster/workspace/retune sub-ports; browser-control, mcp, execution, file-system, subagent, permission, workflow-submit/escalate), an ~90-entry SessionEventType vocabulary (events/session.events.ts:83-174), a pure event reducer folding events→SessionProjection (events/event-reducer.ts), a transient-event retention policy (ModelStreaming/ToolCallProgress/StreamingToolLedgerUpdated/ModelNetworkStatus evicted once their turn is sealed, with a 120 s grace for sealed subagent turns — events/session-event-retention.ts:10-32), trace context via AsyncLocalStorage (tracing/tracer.ts), and telemetry operation/actor vocabularies (telemetry/index.ts).

Not opened (named, not guessed): the 31 contracts port files other than the five read; packages/shared outside zcode-protocol-v4 and the files it re-exports; rpc examples/01-04 demos; the bootstrap v4 host implementation (read only its imports); foundation.ts and ipc.ts bodies.

**Steals.**
- **Two-phase wire validation: route-boundary candidate schema, owned typed faults after** (`zcode-repo/packages/shared/src/zcode-protocol-v4/wire.ts`) - The service boundary validates only what routing needs (topic, subscriptionId) via topicWireFrameCandidateSchema, with payload fields deliberately z.unknown().optional(); full validation and any errors happen in the assembler that owns the subscription, which emits a typed TopicWireAssemblyFault instead of warn-and-drop. The comments document the failure it prevents: early drops left stores waiting forever for a frame that was swallowed (wire.ts:49-82, wire-assembler.ts:1-45). _Estate use:_ Any estate fan-out that streams subagent output through a relay should validate only routing fields at the boundary and defer full schema checks to the owner, so a bad payload surfaces as a typed fault instead of a silent stall.
- **Bounded replay + watermark backpressure on a reliable channel** (`zcode-repo/packages/rpc/src/persistent-protocol.ts`) - ACK-tracked sends accumulate in a replay buffer capped at 8 MiB / 45 s; overflow synchronously abandons the session (Disconnect + onClose) so a locked-screen peer can't grow memory without bound, and unacked bytes drive hysteresis saturate/drain edges (1 MiB / 256 KiB) that let upper layers pause emission while coalescing absorbs the burst (persistent-protocol.ts:29-101,123-143,240-249). _Estate use:_ The estate's long-lived sessions can adopt the same contract: replay what fits, and when it doesn't, declare the session dead and resync from a watermark instead of buffering forever.
- **Semantics-preserving delta coalescing with a byte-identical final-state invariant** (`zcode-repo/packages/shared/src/zcode-protocol-v4/coalesce.ts`) - A closed rule set merges a flush window of deltas (adjacent appends concat, upsert swallows prior deltas, removals are barriers nothing crosses) with the stated contract that coalesce(deltas) applied equals per-delta delivery byte for byte. The workflowRun merge logic documents why it merges into the last same-run op, not the first, with a worked counterexample of a delete-then-add key vanishing (coalesce.ts:1-73). _Estate use:_ Directly applicable to the estate's own event streams: batching must never change replayed state; 'removed' events as merge barriers is the key trick.
- **One reducer, two mirrors: projection and TUI share a pure single-clock state function** (`zcode-repo/packages/shared/src/zcode-protocol-v4/workflow-runs-reducer.ts`) - The workflowRuns state reducer lives in shared precisely so the bootstrap projection and the TUI mirror cannot each grow their own fold — the header calls this the single-clock principle and documents the engine's three structural quirks (resume short-circuits, first-carries-kind) so future readers don't 'fix' them into bugs. Pure function: no Date.now, no IO; the impure identity gates stay in bootstrap. _Estate use:_ When two estate surfaces (CLI mirror and dashboard) render the same run, ship one reducer and let each side feed it, rather than duplicating projection logic that drifts.
- **ProxyChannel: any service object becomes a channel, any channel becomes the service** (`zcode-repo/packages/rpc/src/proxy-channel.ts`) - fromService wraps an object as IServerChannel by naming convention (methods→call, on*→listen, onDynamic*→parameterized listen), buffering events so nothing is lost pre-subscription; toService is an ES6 Proxy that falls back to plain-object semantics for symbol/then probes so React and loggers don't detonate it (proxy-channel.ts:106-146 documents that exact past failure). _Estate use:_ The estate's subagent/tool services could expose the same shape: any object with methods and on* events becomes a callable service over any transport, killing per-service switch-case boilerplate.
- **Turn-window retention: transient streaming events evicted from memory on seal** (`zcode-repo/apps/zcode-cli/packages/contracts/src/events/session-event-retention.ts`) - Four high-frequency event types (model streaming, tool progress, network status) are appended to the same store for sequencing but evicted once their turn is sealed, since finished turns are re-synthesized from persisted messages; a 120 s grace sweep catches sealed subagent turns that never get a successor — the comment cites a real 10K-delta leak this fixed (session-event-retention.ts:10-33). _Estate use:_ Estate transcript/memory stores can apply the same move: keep full fidelity in the durable log, define an explicit allowlist of what may live only briefly in RAM, and time-sweep the stragglers.

**Convergence with the estate.**

**Steals.**

The sole client-side fabrication is an optimisticCommands overlay that is reconciled away the instant the authoritative projection shows the commandId (reconcileOptimistic, line 1294). A 2s watchdog (line 1247) treats 'ACK accepted but projection silent' as a fault and opens same-sub recovery. Content-deterministic faults skip the resume ladder straight to forced snapshot, and timeout finals are kept distinguishable from content faults in telemetry (contentEligible:false, line 953). Generational counters invalidate stale subscriptions. _Estate use:_ This is the estate's engine-owns-truth law already proven at renderer scale. Adopt the same three rules plus the accepted-ACK watchdog for any estate UI that mirrors a run journal: the watcher never writes facts, it only re-syncs when observed reality fails to confirm an acknowledged act.
- **Renderer registry with by-name precedence over family** (`zcode-repo/packages/ui/src/ToolCallBlocks/resolveRenderer.ts`) - A pure function resolves tool call → component in three stages: group kinds, then explicit tool names before family matching (with the rationale in comments: unregistered tools resolve to unknown identity and would otherwise fall into the family's generic fallback card), then a family switch, ending in FallbackToolCallBlock (raw JSON). - **One pure timeline model, three consumers, identity-keyed cache** (`zcode-repo/packages/ui/src/components/workflow-timeline/timeline-model.ts`) - A pure function folds the bounded graph payload plus the run projection into stations/tracks/arcs — 'no React, no DOM, no time' — and chat cards, confirm dialogs, and the sidebar all consume that one model. timeline-cache.ts then memoizes it in a two-level WeakMap keyed by object identity, safe because protocol objects are immutable so identity equals content and weak refs prevent leaks. Side effects (persist, applyTheme) live inside setters, not subscribers. _Estate use:_ For any multi-surface estate UI, the whitelist + replay-through-setters pattern gives cross-window sync without a state library beyond Zustand and without sync storms.
- **Single visual vocabulary for run status** (`zcode-repo/packages/ui/src/components/workflow-graph/run-status-presentation.ts`) - STATUS_DOT / RUN_STATUS_DOT / RUN_STATUS_TEXT define once how 'running/pending/done/failed/stopped' is drawn — pulsing warning lamp for running (not primary: primary reads as emphasis, not motion), neutral empty ring for stopped, destructive reserved solely for errored. ## workflow-engine

**What it is.** This is the machinery this survey is running on. `@zcode/dynamic-workflow` is a pure library holding the TypeScript facade agents write scripts against, a real TypeScript compiler pipeline that recovers rigor from those scripts (typecheck, authoring diagnostics, JSON Schema synthesis for typed asks, four analysis graphs), a lowering pass that rewrites facade calls into `__host.*` calls, and the deterministic execution engine that journals and replays them. `@zcode/dynamic-workflow-runtime` is the sandbox: it spawns a node child process running a vm-realm with only ES intrinsics plus `__host`, and bridges NDJSON to the engine. `@zcode/node-repl-host` is the shared MCP host behind the `js` tool (Browser Use / Computer Use kernels). `debug` is a dev-only Hono + React trace viewer over local logs/SQLite plus a network-capture proxy. What I did not open: the deep analysis internals (`analysis/interpret.ts` transfer rules, `taint.ts`, the causality-order* family), `engine/engine-artifacts.ts`/`engine-world.ts` method bodies, `debug/src` UI components, `node-repl-host` browser/cua bridge bodies, and the production driver in `@zcode/bootstrap` (out of scope). No builds or tests were run — read-only survey of a shallow clone.

**Architecture.** dynamic-workflow (pure, zero-I/O library): `facade/dts.ts` embeds the whole model-facing API as a .d.ts string asset (segments concatenated into FACADE_DTS and a snippet subset). `compiler/compile.ts` wraps the script in `async function __workflowScript__()`, typechecks it in a fully virtual compiler host (script + facade + embedded TS stdlib closure in a Map; `types: []`, ES2022, strict with noUncheckedIndexedAccess deliberately off because models write TS that way). `analysis/sites.ts` walks the checker once to build the site table (ask/actor/world-read/report/artifact sites, keyed `ask#3` style); `analysis/facade-misuse.ts`, `world-run.ts`, `artifacts.ts`, `phases.ts`, `actor-names.ts` are authoring diagnostics; `analysis/interpret.ts` runs a taint fixpoint plus temporal walk to mint AnalysisCore, and four graphs (site, causality, control-flow, handoff) are pure projections of it. `schema/synthesize.ts` emits JSON Schema per typed `ask<T>` from the checker, and `schema/actor-submit-profiles.ts` decides per-actor typed submit_result registration. `lowering/lower.ts` rewrites facade calls to `__host.*` by ts.Node identity (never by name), preserving optional-chain short-circuit with hoisted temporaries, then type-strips. The engine (`engine/engine.ts`, `engine/scheduler.ts`, `engine/types.ts`) is a deterministic state machine over three boundaries: host API (sandbox), driver port (effects + journal + emit), report sink (progress up). It delegates ask lifecycle to AskScheduler (per-actor FIFO, actorSeq admission, repair/nudge, REPAIR_ATTEMPTS=3), journals every event through `engine/journal-memory.ts`'s JournalStorePort, and gates replay ordering through `engine/replay-order.ts`. `engine/imported-cache.ts` implements amend-resume cache consumption; `engine/concurrency.ts` is a pure AIMD controller; `engine/hash.ts` is FNV-1a over canonicalJson. The production driver (actor sessions, SQLite journal) lives outside scope in @zcode/bootstrap per the README boundary contract.

dynamic-workflow-runtime (app-free sandbox): `harness.ts` lowers the script, builds sink-then-driver-then-engine, writes a self-contained ESM entry file to `<cwd>/.zcode/workflow-runs/<runId>.mjs` with the lowered code + args embedded as JSON (dodging Windows' 32,767-char command line), spawns node with ELECTRON_RUN_AS_NODE=1, and bridges NDJSON stdio to the engine with a first-wins finalize; every terminal failure routes through engine.fail/stop so the journal and caller never disagree. `child-source.ts` renders the child from `childMain.toString()`: a vm.createContext realm containing only ES intrinsics plus `__host`, with runtime bans on Date.now/argless new Date/Math.random, and cross-realm convergence (everything the script touches is built inside the context). `protocol.ts` is the typed wire contract (create-actor fire-and-forget, request/response for ask/world-read/publish-artifact, event channel for log/report/declare-artifact/phase-entered, complete).

node-repl-host: `server.ts` is an MCP stdio server exposing a single `js` tool; production executes each call in a fresh Worker thread wrapping a fresh NodeReplSession (module cache destroyed with the call), calls serialized per session key; `browser-bridge.ts`/`cua-bridge.ts` inject domain globals, `cua-broker.ts` multiplexes Computer Use, `process-lifecycle.ts` installs shutdown guards; `tool-contract.ts` keeps serverInfo version and the long model-facing tool description in one place.

debug: `server/index.ts` is a Hono dev server reading only local diagnostics (`server/sources.ts`: ~/.zcode/cli/log/*.jsonl, session db.sqlite read-only, optional event JSONL), with SSE streams (`server/observation-events.ts`) and an http-mitm network-capture proxy (`server/network-capture.ts`); `server/analyzer.ts` derives traces, timelines, spans, context-snapshot/usage and cache reports; a React + vis-timeline UI in `src/` renders them.

**Steals.**
- **Journal-first deterministic engine** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/engine.ts`) - The engine core does no I/O, no clock, no randomness (`engine.ts:2-12`); every host call consults the journal at (siteId, ordinal) before doing work, short-circuits on a hit with zero driver calls, and a defensive inputHash comparison fails the whole run loudly on mismatch instead of silently diverging (`scheduler.ts:128-160`). First run and replay are therefore instruction-identical by construction, not by discipline. _Estate use:_ Make every agent side-effect a keyed, content-hashed journal entry consulted before execution, so any long multi-agent run can be killed and resumed by replaying the log through the same deterministic core.
- **Replay settle-order gate** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/replay-order.ts`) - Resume replays the scheduling, not just the answers: cached settlements are parked until their first-born settle order — recovered from the existing event log with zero schema migration (`recoverSettleOrder`, lines 141-164) — and releases go through a one-microtask FIFO hop (lines 63-83) so Promise.all continuations attach in the same order the original run produced. Without it, a replay of the same deterministic script dies on its own inputHash checks. _Estate use:_ When resuming a partially completed fan-out, park cached results in their recorded completion order and release them through a microtask queue, so post-join ordinals in the re-run land exactly where the first run put them.
- **One-table facade registry with type-derived vocabulary** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/facade/registry.ts`) - A single (container, member) → op row list with `satisfies`-derived op union types drives site collection, misuse diagnostics, lowering and journal inputHashing; identity is judged by declaration container, not name spelling, so `git.log` and top-level `log()` never collide (lines 13-51). Adding a world-read primitive is one row with zero consumer edits. _Estate use:_ Define the agent tool vocabulary in a single typed table and derive tool schemas, journals and code rewriters from it, instead of editing five parallel switch sites whenever a primitive is added.
- **Compile-time rigor from an embedded checker** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/compiler/compile.ts`) - Scripts are typechecked against an embedded facade .d.ts in a fully virtual compiler host with the TS stdlib closure compiled into the bundle (no disk, dev == SEA binary), typed asks get checker-derived JSON Schemas (`schema/synthesize.ts`), and raw compiler errors are rewritten into repair instructions (TS1184 messages name `declare`/`export` and give the fix, lines 166-212). The purity contract starts at compile time: `process`/`fetch` fail typechecking. _Estate use:_ Before executing any model-authored script, run it through an embedded-checker typecheck that also mints result schemas, and phrase diagnostics as the exact edit the model should make.
- **Sandbox with FIFO-ordered fire-and-forget handles** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow-runtime/src/child-source.ts`) - createActor is synchronous inside the vm realm by minting a `local#N` handle and firing a create-actor message; stdio FIFO guarantees the parent maps it before any ask referencing it arrives (`protocol.ts:43-51`, `harness.ts:461-481`). Nondeterminism is banned a second time at runtime (Date subclassed to throw on now()/argless construction, Math.random gutted, lines 227-247), and the payload rides inside the generated entry file to dodge the 32,767-char Windows command line. _Estate use:_ For sandboxed effectful scripts, mirror the sync-handle-plus-FIFO pattern, ban nondeterminism at both compile and runtime layers, and embed spawn payloads in files rather than argv for Windows-safe launches.
- **Amend-resume import cache with diverge-monotonic keys** (`zcode-repo/apps/zcode-cli/packages/dynamic-workflow/src/engine/imported-cache.ts`) - A revised script imports finished work keyed on (actor name, canonicalJson persona, per-actor seq, inputHash); consumption is cursor-based, divergence is monotonic and cascades for free because downstream instructions interpolate new upstream results (lines 41-60). The cache closes on the first observed workspace write — not on any live ask, which measured 6 of 50 cache hits lost — and after closure only provably pure asks (toolCalls===0) still hit (`scheduler.ts:248-267`). _Estate use:_ When re-running a modified multi-agent plan, reuse prior subagent answers keyed on stable names plus input hashes, and invalidate on the first observed workspace mutation rather than on any concurrency.

**Convergence with the estate.**
- engine-owns-truth, and ZCode beats the estate's version: `engine/engine.ts:2-12` states the core does no I/O, reads no clock, uses no randomness — the LLM's script only narrates facade calls while the engine + journal own all state — and determinism is enforced twice (compile-time via `compiler/compile.ts:51-54` types:[] purity, runtime via the Date/Math.random bans in `child-source.ts:227-247`).
- hash-sealed claims registers: every node carries `inputHash` = FNV-1a over canonicalJson (`engine/hash.ts:34-50`), verified defensively on every replay hit with a loud InputHashMismatch run failure (`engine/scheduler.ts:129-135`), and resume refuses a byte-different script via ScriptHashMismatch (`engine/engine.ts:336-348`). Storage is SQLite + an append-only dwf_event log, not markdown, but the seal-over-collection discipline is identical.
- subagent fan-outs pinned to a named model with typed results: `subagentModel` rides the run-launched event (engine never reads it, host reads it back with zero SQL — `engine/types.ts:493-502`), `ActorRecord.resolvedModel` persists the pin so resume re-attaches to the same model (`engine/types.ts:762-775`), and typed asks carry checker-derived JSON Schemas with per-actor submit profiles (`schema/synthesize.ts`, `schema/actor-submit-profiles.ts`).
