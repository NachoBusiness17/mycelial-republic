## Normative contract — NEW SPECULATION

**B.06 — Separate immutable intent, attempts, and effect knowledge. Unproven; high confidence in the need.** An admitted logical operation has one immutable intent. Each delivery has a distinct attempt. Transport outcome is `success / typed_failure / exception / no_return`. Effect knowledge is independently `APPLIED / NOT_APPLIED_FINAL / UNKNOWN`. Store lifecycle transitions as append-only events; never overwrite COMPLETED or FAILED with the fact that a receipt was saved. A tool error after a commit can coexist with APPLIED. `ok:true` is reserved for a verified accepted postcondition, not mere admission or successful logging. Pending/UNKNOWN responses retain the compatible `{ok,result,error}` envelope and include the operation ID and explicit knowledge state in `result`. Old clients must not turn any `ok:false` into a fresh logical operation.

**Change my mind:** a simpler representation demonstrably preserves those distinctions. **Measure/source/check-date:** envelope/schema tests and injected post-commit exception/no-return cases produce the specified independent fields; fixture oracle, C1.

**B.07 — Stable identity must survive replay without merging deliberate repetitions. Unproven; high confidence.** The caller persists a workflow/run ID and decision-slot identity before sending; the admission service transactionally maps `(run_id, decision_id, effect_ordinal, intent_revision)` to a CSPRNG 256-bit operation ID. A lost admission response is retried with that same key. Each logical repeat gets a new decision or effect ordinal, even with identical content. Retries, worker replacements, and generation folds reuse the operation ID. A changed payload or precondition under the same operation ID returns `OPERATION_ID_CONFLICT` without dispatch. A new intent revision requires a recorded supersession relationship; it cannot bypass an unresolved old operation. Attempt IDs are independently random and never replace operation IDs. Canonical payload digests exclude retry count, timestamps, epoch, and transport metadata. Use full SHA-256, with a sealed canonical-encoding specification and test vectors; do not silently normalize paths or arguments after hashing.

**Change my mind:** another identity algorithm passes lost-response, replay, same-ID/different-payload, and legitimate-repeat tests. **Measure/source/check-date:** one operation per admission key, one immutable payload binding per operation, two distinct requested repetitions remain two operations; store uniqueness queries, C1.

**B.08 — Durable intent has the following required schema and admission semantics. Unproven; medium confidence.** The linked [effect-intent-v0.schema.json](./effect-intent-v0.schema.json) is the structural draft. Semantic validation also checks that referenced payload bytes exist and match their digest, authorization permits the exact destination and operation, preconditions are appropriate for the adapter, budgets can be reserved, and the declared adapter build is installed. The admission acknowledgment is sent only after the immutable intent and reservation commit under the registered durability profile. Raw credentials are never stored in the intent; a credential reference binds an independently enforced authorization scope. Requested scope is data, not self-authorization.

**Change my mind:** failure injection exposes an omitted field or invalid transition, or an existing schema passes all checks. **Measure/source/check-date:** all valid calibration vectors accepted, malformed/unauthorized/conflicting vectors rejected before dispatch, and lost admission responses resolve to the original operation; validator output plus receiver trace, C1.

**B.09 — Put the logical effect and its deduplication record in one authoritative transaction. Unproven; high confidence in the requirement, medium in this implementation choice.** The v0 default is a local transactional effect store: a unique operation-ID row and a logical ledger/document/chain event commit atomically. Candidate implementation: one local SQLite database, serialized writer transactions, pinned version/VFS/settings, `journal_mode=WAL`, `synchronous=FULL`; register and verify actual settings per connection. SQLite's durability still depends on the OS/storage contract. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous).

Files, JSONL ledgers, and chain/tip files may be materialized views of this canonical store. A committed logical event is not yet proof that its exported file is current. API success for a task requiring a plain file must wait for that file's independent postcondition. If the current files must remain the sole authoritative state, this database proposal is not a transparent drop-in: build a crash-consistent file protocol and register that different design. A database receipt committed separately from an arbitrary filesystem mutation does not close the atomicity gap.

For a repeated operation ID, return its persisted result after matching the immutable intent digest. Do not execute again. Persist dedup tombstones for at least the maximum replay/backup-retention horizon; restored backups must not re-admit IDs already executed after the restored snapshot.

**Change my mind:** a file-native transaction design meets the same tests without changing authoritative semantics. **Measure/source/check-date:** exactly one canonical effect row per operation; duplicate responses reference identical result digests; restored and replayed runs do not duplicate effects; C1 for a single canonical ledger insert, C2 for the complete registered adapter set.

**B.10 — Fence at the receiver's commit boundary, not at a worker's clock. Unproven; high confidence.** Allocate monotonically increasing owner epochs transactionally per resource. Each dispatch carries its epoch; the receiver atomically compares it with the resource's accepted current epoch in the same transaction that commits the effect and dedup record. Workers have no direct write permission to canonical destinations. Token expiry or a lease file alone is insufficient. For plain-file export, one destination owner holds a kernel-enforced exclusive resource lock from precondition inspection through replacement and completion accounting. Never steal it because time elapsed. Failover waits for release or verified termination of the old writer; a generation bump without exclusion of its open file handles is insufficient.

**Change my mind:** a different receiving-resource protocol rejects delayed writes after ownership changes. **Measure/source/check-date:** suspend owner A after its initial check, advance ownership to B, commit B, resume A; A commits zero effects and receives STALE_EPOCH. Receiver trace and target version history, C1.

**B.11 — Local file effects need versioned desired state and a declared durability profile. Unproven; medium confidence.** Initially permit `file_replace` and create-if-absent only through a declared receiver-owned root. Register canonical path rules for Windows case folding, drive/UNC forms, junctions and reparse points; reject path escape and check-and-swap races. Preconditions are `absent` or an exact expected version and SHA-256, never an optional hint. Stage exact bytes in a uniquely named file on the same filesystem, verify them, flush them, then atomically replace under the destination lock and verify the resulting bytes. Replacing a raw file and recording dedup in another file or DB is not one atomic operation.

Therefore v0 treats canonical transactional documents plus their materializations separately. An immutable version object and authoritative manifest can bind operation identity to bytes; plain exported files remain views. Keep readers behind the manifest/version contract where atomic visibility matters. If unrelated programs can alter raw destinations outside the receiver, autonomous reconciliation for those destinations is excluded until that race is explicitly handled.

Register process-crash durability separately from OS/power-loss durability. Do not equate `write_text`, a successful rename, or a read-after-write with durable storage. POSIX-style parent-directory synchronization is not a portable Windows recipe. The Windows/WSL/Docker mount path must have a tested adapter with explicit file flush and namespace-persistence assumptions; unresolved power-loss behavior remains Unproven. [Python `os.replace` and `os.fsync`](https://docs.python.org/3/library/os.html), [Windows FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

**Change my mind:** platform-specific storage evidence and crashes at each write/flush/replace boundary establish the chosen profile. **Measure/source/check-date:** no torn accepted files, unnoticed precondition conflicts, or false attribution of a file version to an operation; independent bytes/version oracle, C2. Pilot success on a transactional ledger does not qualify file replacement.

**B.12 — Ledgers and chain events need immutable operation records, not append-and-count heuristics. Unproven; high confidence.** Canonical ledger rows require unique operation IDs, payload digests, sequence, resource version, epoch, and predecessor commitment. Allocate sequence and append within one transaction. Export JSONL as a rebuildable view; register framing/checksums and repair of partial export tails. If append-only JSONL remains authoritative, a single receiver must own the append/flush/recovery protocol and dedup index must rebuild from committed records; an independently written sidecar index is not atomic dedup.

For the chain, include operation ID and intent digest in each immutable event. Store content bytes before committing their reference under the same registered persistence policy; an audit can accept neither an absent referenced object nor a mutable replacement under an old content address. Use append-only correction events for operational history. The existing amendable biography can remain a separate projection. Freeze both chain and object-store bytes for HOLD comparisons, as adopted in the v2 request.

**Change my mind:** an existing append protocol establishes these invariants under concurrent writes and crashes. **Measure/source/check-date:** full reconstruction from canonical events yields the committed rows/root, object digests, and operation index; no accepted malformed tail or overwritten event; C2.

**B.13 — UNKNOWN is a durable hold until the old request cannot commit or the effect is confirmed. Unproven; high confidence.** Timeouts, missing return rows, receipt-write failure after dispatch, and ambiguous postconditions enter UNKNOWN. Do not reset the failure counter, release the operation reservation, or mint a replacement operation to evade the hold. Recovery may read and reconcile; it must not redispatch an effect without destination dedup or final-negative evidence.

Reconciliation request: `query_operation(destination_id, operation_id, intent_digest, minimum_epoch)` returns (a) `APPLIED` with operation-bound commit evidence and postcondition, (b) `NOT_APPLIED_FINAL` with a receiver-authenticated cancellation/fence barrier proving all prior attempts cannot later commit, or (c) `UNKNOWN` with the observed state and missing proof. Same-ID/different-payload is a conflict, never NOT_APPLIED_FINAL.

For destinations lacking dedup, acquire exclusive destination ownership, fence or definitively stop all previous senders/writers, drain/cancel in-flight requests, then inspect operation-specific evidence. If the result merely matches the desired bytes without operation provenance, record `POSTCONDITION_SATISFIED_PROVENANCE_UNKNOWN`; do not claim this operation performed it. Current absence or unchanged bytes cannot prove final nonapplication while an old call can still arrive. If neither applied evidence nor an enforceable finality barrier exists, UNKNOWN persists. A human can authorize a new bounded action while accepting uncertainty, but that does not retroactively prove the old result.

**Change my mind:** a specific receiver has stronger operation-status/finality semantics. **Measure/source/check-date:** delay an original call, obtain an absence read, and resume it; the reconciler must not authorize an unsafe retry. With an enforced barrier, its final-negative response must remain true after all delayed calls are released; fixture oracle, C1/C2.

## Acceptance and pilot

**B.14 — The minimum honest pilot is one canonical ledger operation with commit-before-response death. Unproven; medium confidence.** Fleet builds the receiver/store adapter and fault hook; this draft supplies the contract; operator selects and protects a disposable destination; the single worker runs the sealed case. Inject termination after the canonical effect and dedup commit, before API response. Restart, retry the same operation, and reconcile. Required evidence: one admitted intent, at least two attempts, exactly one committed ledger row, immutable intent binding, correct APPLIED response with the original result, and no intervention hidden from the event journal. Seal code/configuration/schema, fixture data, destination initial bytes, worker/verifier digests, clock source, and expected invariant before executing.

The pilot supports only this adapter, build, boundary, and process-crash scope. Add calibrations for same ID/different payload, rejected authorization, a deliberately broken dedup adapter that the verifier must reject, and paused-old-owner fencing. Calibration executions do not count as the one scored pilot case. No random negative result can stand in for deliberate known-bad calibration.

**Change my mind:** a cheaper pilot exercises the same ambiguity gap and has an equally independent destination oracle. **Measure/source/check-date:** all registered predicates and negative calibrations pass; frozen inputs, receiver journal, independent ledger read, and committed worker verdict; C1.

**B.15 — Full seal requires every admitted effect class to have a receiving-resource contract. Unproven; high confidence.** Register route coverage, adapter identity, authority and budget enforcement, operation status query, dedup retention, fencing, preconditions, durability scope, and postcondition verifier per class. Read-only calls may use weaker effect rules but still need attempt accounting. Arbitrary shell/Python calls that can mutate unknown destinations cannot receive an autonomous retry guarantee merely by passing through this API; isolate them to effectless sandboxes or require explicit typed adapters for their mutations. Unknown classes fail admission.

Run fault boundaries before intent acknowledgment; after durable intent but before dispatch; after dispatch before commit; after commit before response; and during receipt/checkpoint recovery. Cover concurrency 1, 2, and 8 only after the independent host-feasibility gate admits each level. Include disk full, partial writes, telemetry failure, stale owner, duplicate delivery, mismatched payload, and restore from an older snapshot. Block release on a single unauthorized, duplicate, stale-owner, or falsely successful committed effect. Inconclusive storage evidence remains Unproven.

**Change my mind:** the declared route surface narrows or additional failure modes demand more cases. **Measure/source/check-date:** frozen adapter manifest and fault-oracle comparison show zero invariant counterexamples and no missing admitted intents; C2. Passing supports only the registered implementation and failure envelope.

**B.16 — The Windows liveness probe requires target-runtime calibration; the draft's unconditional-termination inference is retracted. Supported portability concern; high confidence. Actual production harm: Unproven.** Captured `mag/verkle_knot.py:108–110` calls `os.kill(owner, 0)`. On the observed Windows Python 3.12.14 runtime, `signal.CTRL_C_EVENT` equals zero. The [CPython 3.12 implementation](https://raw.githubusercontent.com/python/cpython/3.12/Modules/posixmodule.c) handles that value through console-control signaling when Windows console I/O is enabled, rather than the Unix existence probe. The [documentation](https://docs.python.org/3.12/library/os.html#os.kill) makes CTRL_C_EVENT a special case; overlooking its numeric value produced the incorrect draft inference.

An isolated calibration created its own hidden child, waited for readiness, called `os.kill(child.pid, 0)`, and observed the child still running two seconds later; it then explicitly cleaned up only that child. Receipt: [windows-liveness-calibration.json](./windows-liveness-calibration.json). No production lock or owner was touched. This refutes unconditional termination on this tested path; it does not establish a harmless, accurate existence probe across console configurations, deployed runtimes, or PID reuse.

**NEW SPECULATION requirement:** use a non-mutating platform-specific process query binding PID to start time, and never treat marker age as proof of death. **Change my mind:** an equivalent target-runtime implementation passes live/exited/PID-reuse and ownership tests. **Measure/source/check-date:** a disposable live owner survives contender probes, exited owners are identified, and stale owners cannot commit; independent process observer and receiver trace on the actual deployed runtime, C1. Failure of those checks blocks that adapter, without claiming an unobserved production termination.
