## 4 — Recovery and effect-broker contract v0

**4.1 — The named HTTP seam bypasses the named effect broker. **4.2 — Recovery fails first at concurrency one, after commit and before receipt. Unproven runtime outcome; high confidence in the gap.** M:44 “re-issue only unrecorded side effects”; V1:4.2. One ledger append can succeed and lose its response. Reissuing because the response is absent can append twice. At concurrency two, paused owners and check-then-write races add stale writes. **4.3 — Accept the following contract as the proposed closure, not as an implemented feature. Unproven; medium confidence in this design choice. NEW SPECULATION.** Full normative details: [effect-broker-contract-v0.md](./effect-broker-contract-v0.md), B.06–B.15; machine-readable [intent schema](./effect-intent-v0.schema.json).

- Durable immutable intent binds operation ID, run/admission key, principal, destination/resource/scope, effect type, payload bytes/hash, exact precondition, postcondition verifier, grant/policy/credential reference, persistent reservation, adapter build, durability profile and replay horizon. The schema's semantic validator must enforce authority, references and destination-specific preconditions.
- Persist `(run_id, decision_id, effect_ordinal, intent_revision)` before admission; atomically map it to one 256-bit CSPRNG operation ID. Lost responses, retries and folds reuse that ID. Deliberate identical repetitions get different logical identities. Same ID plus changed intent is rejected.
- Journal attempts separately. Transport status and effect knowledge are separate. `APPLIED / NOT_APPLIED_FINAL / UNKNOWN` are not three spellings of HTTP success/failure. `ok:true` requires the task's verified postcondition.
- Commit the logical effect and unique dedup row in the same authoritative transaction. Proposed v0 uses a pinned local SQLite store. JSONL/files/chain exports become explicit materialized views; their visibility must be independently verified. A DB receipt written separately from a raw file mutation does not provide atomic deduplication.
- Enforce monotonically increasing ownership epochs at the receiver's commit boundary. Block direct destination writes. Dedup records survive the replay and backup horizon; an old restore cannot re-admit effects already committed later.
- `query_operation(destination_id, operation_id, intent_digest, minimum_epoch)` returns APPLIED with operation-bound evidence, NOT_APPLIED_FINAL with an enforceable cancellation/fence barrier, or UNKNOWN. Current absence is not finality. Matching desired bytes without operation provenance is `POSTCONDITION_SATISFIED_PROVENANCE_UNKNOWN`.
- UNKNOWN survives timeout, restart and fold. No new ID, released reservation or nondeduplicated redispatch may evade it. Arbitrary mutating shell/Python commands remain outside unattended recovery until wrapped in typed receiving-resource contracts.

**Change my mind / resolution:** C1 one-ledger pilot, conflict/authorization/stale-owner/broken-dedup calibrations; C2 every admitted adapter passes its declared fault/durability envelope. File-authoritative alternatives are acceptable if independently proved; this draft does not silently redefine existing files as transactional.

**4.4 — The HOLD-3/M delivery is a pre-seal build package, not a seal. Supported artifact status; high confidence.** User TASK 4; H3.2–H3.7. [HOLD-3M-seal-package-v0.md](./HOLD-3M-seal-package-v0.md) gives exact artifact names, owners, contents and acceptance checks in K.2–K.13; the meter contract in K.14; distinct verifier skeleton contracts and commitment/reveal order in K.15; known-bad calibrations in K.16.
