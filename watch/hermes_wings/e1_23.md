(1) What it does
Documents a second, identity-aware phone path to the containerized OpenClaw Gateway: a phone browser reaches Cloudflare Access (identity/MFA/policy), then a Cloudflare Tunnel (outbound-only) into a cloudflared-openclaw container that shares the OpenClaw network namespace and forwards to 127.0.0.1:18789. It gives dashboard setup steps (remotely managed tunnel, published application route, self-hosted Access app with explicit Allow policy), token handling in an uncommitted .env, start/verify commands, and rollback.

(2) Notable design patterns
- Layered boundary: Cloudflare "adds an outer identity boundary"; the existing Gateway token is kept unchanged.
- Deny-by-default with explicit allow: Access requires an explicit Allow policy for the operator; Everyone, Bypass, and unauthenticated routes are forbidden.
- Break-glass fallback: the Tailscale Serve route stays tailnet-only as the recovery path, with rollback being a single compose stop.

(3) Risks
- Single point of failure: one tunnel, one connector container, one published hostname; the doc itself warns the phone path dies if Cloudflare policy or DNS is misconfigured, and recovery is manual.
- Shared state: the connector joins the shared namespace, reaching the gateway's loopback port; the tunnel token is one shared .env secret (holder can run a connector).
- Duplicate scheduler: none — the file has no scheduler or timer; startup and rollback are manual docker compose commands.
