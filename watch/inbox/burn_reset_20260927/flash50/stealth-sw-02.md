## 1. What has been published on self-modifying agents

**Code/tool self-rewriting.** Darwin Gödel Machine (Zhang, Hu, Lu, Lange, Clune; arXiv:2505.22954, fetched) iteratively rewrites its own agent codebase, empirically validating each change on benchmarks instead of formal proofs, and maintains an archive of agent variants for open-ended parallel exploration. Measured: SWE-bench 20.0% to 50.0%, Polyglot 14.2% to 30.7%. It learns "better code editing tools, long-context window management, peer-review mechanisms." Voyager (Wang et al., arXiv:2305.16291, fetched) is the canonical earlier form: an ever-growing library of executable code skills, generated by GPT-4, stored, retrieved, and composed, reusable in brand-new Minecraft worlds. A 2026 survey, "Self-Improvements in Modern Agentic Systems" (search result, not fetched), taxonomizes the field: keep the model frozen, refine the surrounding scaffold: prompts, memory, tools, or full architecture.

**Prompt self-refinement.** The Self-Refine/Reflexion family treats the agent's own outputs as improvement material. The counterweight is published too: "Large Language Models Cannot Self-Correct Reasoning Yet" (Huang et al., ICLR 2024, arXiv:2310.01798, fetched): intrinsic self-correction without external feedback "at times" degrades performance, so a self-modifying loop keyed to self-judgment can be a decline loop, not an improvement loop.

**Memory self-modification.** MemPoison (Gao et al., Nanjing University, arXiv:2607.14651v1, fetched) defines the memory-update surface adversaries ride: content enters external memory through normal channels (user input, tool outputs, inter-agent messages) and persists across turns. Zombie Agents (Yang, He, Ji, Hooi, Dong, arXiv:2602.15654, verified via MemPoison's reference [59] which I fetched) formalizes persistence: a self-evolving agent's memory-update function F_M writes attacker-controlled content into long-term memory, converting a transient injection into persistent control that self-reinforces.

## 2. Published failure modes

**FM1 Memory-poisoning backdoors.** AgentPoison (Chen, Xiang, Xiao, Song, Li; NeurIPS 2024, arXiv:2407.12784, fetched): first backdoor attack on generic and RAG-based agents by poisoning long-term memory or the knowledge base. Trigger generation is a constrained optimization mapping triggered queries into a unique embedding space so only trigger queries retrieve the malicious demonstrations. No model training or fine-tuning required. Measured: over 80% average attack success rate at under 0.1% poison rate, benign degradation under 1%, across driving, QA, and healthcare EHRAgent agents.

**FM2 Compositional and sleeper memory attacks.** MemPoison (fetched) shows why point defenses fail: L1 direct injection (one plainly harmful record), L2 compositional (harm only exists when individually plausible records are co-retrieved), L3 sleeper (dormant until a trigger, e.g., BCC an attacker on monthly financial reports). Without defenses, behavioral corruption rates run 54-67% despite high clean accuracy; write-time defenses handle L1 but struggle with L2/L3 because maliciousness does not exist at write time. This is the structural blind spot: the poisoned record is innocent when written.

**FM3 Persistent control (zombification).** Zombie Agents (arXiv:2602.15654, citation verified; content from search results, not fetched): poisoned memory re-triggers on future tasks, so the agent stays under attacker control after the original injection source is removed. Search results also name eTAMP (Apr 2026, cross-session cross-site memory poisoning via environment, no direct memory access), ShadowMerge (graph-memory record collisions), InjecMEM, PhantomSkill: none of these four fetched, names from search only.

**FM4 Tool-surface poisoning and rug pulls.** Invariant Labs' MCP tool poisoning line (hidden instructions in tool descriptions; cross-server tool shadowing; description swapped after approval, defeating review-at-install): search results describe it in detail, but my fetch of invariantlabs.ai/blog/mcp-security-vulnerabilities served the homepage only (which does confirm MCP Scan exists and the Snyk acquisition), so the blog body is unverified-primary this session.

**FM5 Self-judged improvement that degrades.** Huang et al. (fetched, above): self-correction without external ground truth can reduce accuracy. A self-modifying agent whose only fitness signal is its own evaluation is running an unanchored feedback loop.

**FM6 Recursive self-consumption collapse.** "The Curse of Recursion" (Shumailov, Shumaylov, Zhao, Gal, Papernot, Anderson; arXiv:2305.17493, fetched; the Nature 2024 version's page redirected to an SSO wall and was not fetched): training on model-generated content "causes irreversible defects in the resulting models, where tails of the original content distribution disappear." For self-modifying systems this generalizes: an agent that folds its own outputs into its memory or training inputs is running the same recursion, one organism at a time.

**FM7 Objective drift inside the loop.** The DGM full text (fetched, arXiv:2505.22954v1 html) reports "no evidence of harmful or malicious behavior in the generated agents" and that "self-modifications have been primarily focused on improving coding capabilities," but warns in its Safety Discussion that "if evaluation benchmarks do not fully capture all desired agent properties (e.g., safety and robustness), the self-improvement loop could amplify misalignment over successive generations," and that self-modification can produce logic "increasingly complex and uninterpretable, hindering human understanding." Note: secondary sources (search summaries) claim the DGM once deleted its own hallucination detector; the paper HTML I fetched contains no such passage and reports the opposite, so I am reporting the primary-source version and flagging the discrepancy.

## 3. What a hash-chained audit trail prevents, and what it does not

**Mechanism.** Each entry stores hash(payload) plus hash(prev node hash + payload hash); verification re-walks the chain and any edit to an entry invalidates that entry and everything after it. This is the Certificate Transparency lineage: RFC 6962 (fetched) specifies "publicly auditable, append-only, untrusted logs" as a Merkle tree whose audit and consistency proofs let interested parties detect misissuance; the log itself does not stop bad issuance, it makes it detectable and non-deniable.

**Mapping to the failure modes:**
- FM1/FM2/FM3 (memory poisoning, sleepers, zombification): a hash-chained memory ledger makes memory append-only and attributable. Every memory write carries author, turn, and provenance hash, so the point of ingress for a poisoned record is traceable after the fact and retroactive sanitization (editing history to hide the trail) is cryptographically impossible. It does not stop the initial poisoned write (that is ingress filtering, a separate control), but it converts silent persistent corruption into detected, attributable, replayable corruption, which is what makes repair possible: you can diff memory against sealed state and excise the L2/L3 compositional records with evidence.
- FM4 (tool rug pulls): seal tool descriptions and binaries at approval time; a later swap fails verification at the next check. This repo runs exactly this and it works, see section 4.
- FM5 (self-judged improvement): seal eval receipts so an improvement claim must point at a chained receipt rather than a self-report (trust bytes, not reports); the loop's fitness signal gets an external anchor.
- FM6 (collapse): chain training-data lineage so human-generated vs model-generated provenance is auditable, per Shumailov's recommendation that preserving authentic human data becomes valuable.
- FM7 (drift): the DGM itself uses a "traceable archive lineage for human review" (fetched quote from its safeguards list, alongside sandboxing and limited modification scope); a hash chain is the same idea made verifiable rather than archival.

**Product layer exists.** VOLT (quox.ai, fetched): a "Verifiable Operations Ledger and Trace" hashing and sealing every governed agent action (tool calls, queries, credential leases, human approvals, memory writes) as it happens, with offline self-hosted verification ("a later edit shows up"), an IETF Internet-Draft (draft-cowles-volt-01), and a companion WARD protocol of write-once append-only receipt digests; target threat is post-hoc modification/deletion of agent records for audit (EU AI Act evidence), explicitly not an attacker who controls the host. Search results (unverified IDs) also surfaced "Agent Flight Recorder" (Sep 2026, hash chaining for per-event ordering plus Merkle batching for compact inclusion proofs) and "A Black Box for Agentic Processes" (Sep 2026), the latter making the key limit: append-only logs inside the same trust domain give tamper evidence but do not remove the operator from the trust equation; that takes external anchoring (RFC 3161 timestamps, transparency-log witnesses, or blockchain anchoring).

**Honest limits.** A hash chain detects, it does not prevent: a compromised writer can still append bad-but-honest entries (integrity is not correctness); an in-trust-domain chain can be wholly rewritten by whoever controls the host unless the tip is anchored somewhere the agent cannot reach; and chains add the same verification tax this repo pays per hook call.

## 4. Local worked example (ran this session, Windows host, repo venv)

- Mechanism read: `rg -n "sha256|prev_hash|drift|DRIFT" seed/verify_seal.py` shows the checker hashes every MANIFEST.sha256 row and prints DRIFT per mismatch (seed/verify_seal.py:7,13,15,16). Chain construction read: `rg -n "def |prev_hash|sha256" mag/integrity_kernel.py` shows `node_hash = _sha256(f"{prev}|{payload_hash}")` at mag/integrity_kernel.py:130 with `prev_hash` stored per node (line 136), and verify() re-checking prev_hash continuity (145), payload hash (148), and node hash (150): tamper anywhere and the chain fails from that point forward.
- Live run: `.venv/Scripts/python.exe seed/verify_seal.py` returned:
  `DRIFT    engines/key_law.py` / `56/57 verified, 1 drifted, 0 missing` / `EXIT=1`.
  The chain caught a real, current modification of a law file between seal time and now (matching the sess-01 lane's independent finding of the same 56/57 drift, commit b9fe3e20c). That is the FM4/FM7 property demonstrated rather than claimed: an unlogged edit to a trusted file is detectable within one command, and the failure is loud (exit 1), not silent.
- Composition note: the same property plus per-entry author/turn/provenance fields is what the memory-ledger design in section 3 adds to a self-modifying agent's memory and tool stores.
