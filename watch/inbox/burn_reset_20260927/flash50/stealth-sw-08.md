# stealth-sw-08: Prompt compression - LLMLingua, gisting, and the achievable-ratio landscape

Researched 2026-09-28 by lane stealth-sw-08. Method: every headline number below was verified this session by fetching the paper's arXiv abstract page or the arXiv API Atom feed (or the microsoft/LLMLingua GitHub README where noted). Two arXiv IDs this lane initially recalled from memory were WRONG (2307.11003 and 2306.11657 both resolve to unrelated astrophysics papers; 2308.08475 and 2309.17368 are also unrelated), so the ID-to-claim mapping below rests on fetched abstracts, not recall. Anything I could not verify is explicitly marked NOT VERIFIED at the end.

## 1. Hard-prompt (token-dropping) methods - model-free, training-free

**LLMLingua** (arXiv:2310.05736, EMNLP 2023, Jiang et al., Microsoft). Abstract: "allows for up to 20x compression with little performance loss". Method: coarse-to-fine compression with a budget controller (to maintain semantic integrity under high ratios) plus token-level iterative compression (to model interdependence between kept tokens); instruction-tuning based distribution alignment between compressor and target. Evaluated on GSM8K, BBH, ShareGPT, Arxiv-March23. The compressor is a SMALL model - GitHub README (github.com/microsoft/LLMLingua) says "a compact, well-trained language model (e.g., GPT2-small, LLaMA-7B)" and lists runnable configs incl. phi-2 and a GPTQ Llama-2-7b needing <8GB VRAM. API: `pip install llmlingua`, `PromptCompressor().compress_prompt(..., rate=..., target_token=...)`; also `structured_compress_prompt` with `<llmlingua>` tags for per-section rates. Integrated into LangChain, LlamaIndex, Prompt Flow.

**LLMLingua-2** (arXiv:2403.12968, Findings ACL 2024). Reframes compression as TOKEN CLASSIFICATION trained by data distillation from an LLM (abstract says "an LLM" without naming it; the README says GPT-4 distillation; models released are XLM-RoBERTa-large and BERT-base-multilingual variants, trained on MeetingBank). Abstract claims: compression ratios of 2x-5x, "3x-6x faster than existing prompt compression methods", end-to-end latency acceleration 1.6x-2.9x, robust generalization across LLMs (in-domain and out-of-domain on MeetingBank, LongBench, ZeroScrolls, GSM8K, BBH).

**LongLLMLingua** (arXiv:2310.06839, ACL 2024). Adds question-aware coarse ranking + document reordering (attacks "lost in the middle"). Abstract claims: compresses ~10k-token prompts "at ratios of 2x-6x", "boosts performance by up to 21.4% with around 4x fewer tokens in GPT-3.5-Turbo" (NaturalQuestions), "94.0% cost reduction in the LooGLE benchmark", end-to-end latency 1.4x-2.6x. Note the pattern: in RAG-style long contexts, compression can IMPROVE accuracy (4x fewer tokens AND up to 21.4% better) because dropped content is noise the target model would have tripped on.

**Selective Context** (arXiv:2304.12102, Li et al., ACL 2023 Findings). Self-information-based content filtering: uses a small causal LM's own perplexity to filter low-information tokens/phrases/sentences; evaluated on summarization and QA. The v1 abstract I fetched contains NO numeric ratio claim. The often-quoted "~50% of content units droppable" figure: NOT VERIFIED this session (Semantic Scholar API returned 429, arXiv v3 abs page 404) - do not treat that 50% as confirmed here.

**RECOMP** (arXiv:2310.04408, Xu, Shi, Choi) - RAG-specific. Trains an extractive compressor (selects useful sentences) and an abstractive compressor (synthesizes summaries across documents), replacing full retrieved text in augmented LMs. Abstract: "a compression rate of as low as 6% with minimal loss in performance" on language modeling and open-domain QA - i.e. keep about 1/17 of the retrieved text. Selective augmentation: compressors "can return an empty string" for irrelevant documents. Also "significantly outperform the off-the-shelf summarization models" and transfer across LMs on the LM task.

## 2. Soft-prompt / learned-embedding methods - trained, model-bound, highest ratios

**Gist tokens** (arXiv:2304.08467, ICLR 2024, Mu, Li, Goodman). Trains the LM ITSELF to compress prompts into "gist" tokens via modified attention masks; training cost is folded into standard instruction fine-tuning. Abstract claims: applied to LLaMA-7B and FLAN-T5-XXL, "up to 26x compression of prompts", "up to 40% FLOPs reductions", 4.2% wall-time speedup, with minimal quality loss; gist tokens can be cached and reused across calls. Key constraint: this is not a bolt-on tool - the deployed model must be fine-tuned, so it fits only self-hosted stacks.

**ICAE / In-context Autoencoder** (arXiv:2307.06945, ICLR 2024, Ge et al., Microsoft). Pretrains a lightweight encoder with autoencoding + LM objectives on big corpora, then instruction fine-tunes it; the target LLM conditions on "short compact memory slots" instead of the raw text. Abstract: ~1% extra parameters, "4x context compression based on Llama", improved inference latency and GPU memory.

**500xCompressor** (arXiv:2408.03094). Compresses context into KV-cache values via a trainable compressor feeding the LLM. Abstract claims: "compression ratios ranging from 6x to 480x", down to "a minimum of one single special token", only ~0.3% additional parameters; argues "K V values have significant advantages over embeddings in preserving information at high compression ratios". Honest cost side: on strictly unseen QA datasets the LLM "retained 62.26-72.89% of its capabilities compared to using non-compressed prompts". The "500x" is the method name, not an achieved ratio.

**AutoCompressor** (arXiv:2305.14788, Chevalier, Wettig, Ajith, Chen - "Adapting Language Models to Compress Contexts"). Recursively processes documents in segments, emitting "summary vectors" that act as soft prompts; fine-tuned OPT and Llama-2 on sequences up to 30,720 tokens; improved long-context perplexity; summary vectors can replace plain-text ICL demos with higher accuracy and lower inference cost; reusable pre-computed vectors for RAG and re-ranking. The abstract states NO numeric compression ratio (a "~40:1" figure floating in secondary sources is NOT VERIFIED by the abstract - ratio is whatever you allocate in summary tokens per chunk).

**xRAG** (arXiv:2405.13792, NeurIPS 2024). RAG extreme case: fuses the dense-retriever's document EMBEDDING into the LLM's representation space, so each retrieved doc costs ONE token of context instead of hundreds. Abstract: "average improvement of over 10% across six knowledge-intensive tasks" while cutting "overall FLOPs by a factor of 3.53"; only the modality bridge is trained (retriever and LLM frozen, plug-and-play, reuses existing embeddings).

## 3. What the 2026 production literature says (ratio vs reality)

From the arXiv API title search on "prompt compression" (54 results, newest 20 reviewed):

- **Prompt Compression in the Wild** (arXiv:2604.02985, ECIR 2026): first systematic large-scale latency study, "thousands of runs and 30,000 queries" across open-source LLMs and three GPU classes. "LLMLingua achieves up to 18% end-to-end speed-ups, when prompt length, compression ratio, and hardware capacity are well matched", with quality statistically unchanged (summarization, codegen, QA). Outside that operating window "the compression step dominates and cancels out the gains". Also: compression can shrink memory enough to offload from datacenter GPUs to commodity cards at +0.3s latency.
- **Prompt Compression in Production Task Orchestration** (arXiv:2603.23525): pre-registered six-arm RCT on production multi-agent orchestration, Claude Sonnet 4.5, 358 successful runs from 1,199 real instructions. r=0.5 retention cut mean total cost 27.9%; r=0.2 (aggressive) INCREASED mean cost 1.8% despite input reduction, due to output expansion (1.03x) and heavy-tailed uncertainty. Conclusion verbatim: "'compress more' is not a reliable production heuristic"; output tokens must be treated as a first-class outcome.
- **Compression as attack surface**: "When Compression Becomes an Attack Surface" (arXiv:2510.22963) - black-box attack (COMA) exploiting information loss in agent compressors. A compressed prompt is also a smaller audit surface.
- Smaller 2026 datapoints (claims as summarized in the API feed I read): Lexical Prompt Compression, training-free deterministic CPU pipeline, "a mean token reduction of 40.3%"; Activation Aggregation compresses to a single activation vector with under 2% accuracy drop; AGORA agent compressor 1.3-13.3x realized; dictionary-encoding lossless compression "up to 80%" on repetitive data; Spectral-LSH observes a "compression-ratio phase transition" around 4x-8x; on diffusion LLMs (LLaDA), LLMLingua-2 at ~50% compression degraded reasoning despite high semantic similarity.

## 4. Synthesis: what ratios are achievable, band by band

1. **2x-5x is the safe, drop-in band.** LLMLingua-2's headline operating range (2x-5x) with 1.6x-2.9x end-to-end latency wins and quality intact; LongLLMLingua's 2x-6x. Training-free, works on black-box APIs, library support exists (llmlingua pip package).
2. **Up to 20x with little loss is the hard-compression headline** (LLMLingua, arXiv:2310.05736), but it needs budget control for semantic integrity and the ECIR 2026 in-the-wild study caps realized END-TO-END speedup at ~18% because compressor latency is paid back only when prompts are long, ratios moderate, and hardware matched.
3. **In compressible context, compression can be a free win**: RECOMP keeps as little as 6% of retrieved text (~17x) with minimal loss, xRAG spends 1 token per document with 3.53x FLOPs cut and +10% quality, LongLLMLingua gets +21.4% accuracy at 4x fewer tokens. The mechanism is selection: retrieved noise and mid-context dilution hurt more than dropping does.
4. **26x-480x is the soft-token ceiling, and it is not free**: gisting (26x, up to 40% FLOPs cut) requires fine-tuning the deployed model itself; 500xCompressor (6x-480x, min 1 token) retains only 62-73% of capability on unseen tasks at the extreme. These bind you to a specific checkpoint; no black-box API can consume soft tokens or KV slots.
5. **Ratio is not savings.** The 2026 RCT shows r=0.2 can cost MORE than uncompressed (output expansion); the ECIR study shows the same ratio can be a speedup or a slowdown depending on hardware and prompt length. Papers also define ratio inconsistently - "compression rate 6%" (RECOMP) means 17x reduction, while "compression ratio 20x" means 5% kept. Never compare a kept-fraction to a reduction factor.

**Estate tie-in:** this harness already runs its own lossy compression pipeline - the context_pack render ladder (commit 727b19b13, environment context) measured fast=True renders falling from 27,218 to 4,496 chars in full mode (16.5% survival) with rung 4 hard-clipping the tail and destroying the task brief in 5 of 6 modes, and "moderate" rungs surviving better than aggressive ones. That matches the literature exactly: aggressive compression destroys tail-critical content (instructions, task briefs), which is the same failure the 2026 RCT measured as r=0.2 backfiring and the COMA attack paper exploits.
