## The concept, grounded in the estate

The item name is the inverse of `mag/gap_map.py`: gap_map reads the cost
ledger and flags a task shape as a FRONTIER GAP when the cheap system's
success rate on it is below the bar ("Cheap success below this = frontier
gap", `mag/gap_map.py` SUCCESS_BAR 0.6, per-shape n>=2 rule at the same file;
`mag/frontier_help.py` percolates those shapes as "task-shape X - cheap
success below bar" asks). Q-049 transposes that exact rule onto the candidate
ledger, where the task shape is the candidate `kind` and the cheap marker is
`local_feasible` (the reading Q-002 canonized in tools/auto_promote.py).

## The gate, exactly

A task shape (candidate kind) is a frontier gap when ALL hold
(deterministic, fail-closed):

1. Its CHEAP terminal outcomes number >= `min_terminal` (2): rows with
   `local_feasible` true ("true"/"yes"/bool True, the auto_promote string
   reading) AND terminal status. `promoted` counts a cheap success,
   `rejected` a cheap failure. Open rows (new/hold) are not outcomes and
   stay out of the rate.
2. cheap success rate = promoted/terminal < `success_bar` (0.6, gap_map's
   bar; `<` is strict, so exactly 0.6 is not a gap).

Every row then routed to the demotion path must itself be: explicit kind ==
a gap shape (43 of 192 rows at session start are kind-less, plus this session
the ledger grew to 196; kind-less rows are never touched), `local_feasible`
true (a row that never claimed cheap is not routed by the shape's
cheap-condemnation; found live during this session: c-905bf4042572, a vllm
GitHub release scrape with feasible "unknown", stays), and status
new/hold (terminal and already-demoted rows are never re-touched).

Demotion = status "demoted" written through `mag.improve.update_candidate_status`
(the single status writer) with an `auto-demote:` note plus
`demote_shape`/`demote_rate` provenance, and one audit row per decision in
`memory/improve/demoted.jsonl` (mirrors `memory/improve/auto_promote.jsonl`).

Why the new status is safe: `rank_candidates_for_brief` surfaces only
new/hold (mag/improve.py), the Q-002 auto-promote gate touches only new/hold
(tools/auto_promote.py OPEN_STATUSES), and no main.py/dashboard consumer
enumerates candidate statuses, so "demoted" simply leaves the promote
surface. Not wired into improve_once (the ask did not ask for wiring);
standalone CLI only.
