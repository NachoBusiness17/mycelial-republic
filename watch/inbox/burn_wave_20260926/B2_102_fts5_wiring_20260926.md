## Falsifier

1. Any corpus_search over a fresh db that returns engine=scan without an index_state/index_note naming why, or a stale db that still returns engine=fts5, kills the never-silently-stale claim. tests/test_corpus_fts.py pins both directions on mtime, bytes, and garbage-db arms.
2. The parity_note claims token-prefix vs substring; a future tokenizer change (unicode61 default in the build script) that silently alters which mid-token rows are missed would make the note lie. The pinned test catches a regression only on the noblegarden shape; any other shape can drift undetected until a caller census (self-fed B2-464).
3. The freshness gate is cheap (mtime + size + one-row probe), not a full hash: a same-size catalog rewrite with a backdated mtime passes the per-search gate. The --deep sha256 tier exists for exactly this and is audit-only; if that adversarial case matters operationally, the self-fed B2-465 daily task must run --deep.
4. The 10.308s rebuild and the live A/B timings are this host, warm cache, Sep-18 map; a cold cache or a v4 map rescan can move them. The verdict does not depend on the exact numbers, only on the class gap (milliseconds vs seconds), which has two independent measurements (B2-22 spike and this lane).
5. corpus_stats and corpus_get remain scan/path-based; only corpus_search gained the index. Any claim that the whole surface got faster would be false; the receipt scopes the win to corpus_search with terms.
