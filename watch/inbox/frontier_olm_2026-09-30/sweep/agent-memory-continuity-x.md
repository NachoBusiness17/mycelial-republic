## Answers to the five research questions

### Q1. Id-resolution and edge-integrity discipline (the 823/825 dangling-edge class)

There IS a published id-normalization discipline, and it is directly stealable before applying the graph.md:37 three-fix list. Paul Iusztin, "Keep Knowledge Graph Clean" (decodingai.com, 2026-06-02, fetched in full this session), splits the exact defect our builder has into two governed stages: extraction-time **resolution** (normalize the name against same-type existing nodes via exact -> fuzzy -> semantic short-circuit; only `canonical_name` and an alias list are touched, never a merge) and load-time **deduplication** (identity decision over full node context, score = 0.7 x embedding + 0.3 x fuzzy; >=0.95 auto-merge, 0.85-0.95 flagged for human review as `(:Entity)-[:SAME_AS {status:'pending'}]->(:Entity)`, <0.85 new node; flagged sources tombstoned, still queryable but skipped in matching; matching type-gated; nightly "dream pass" re-runs dedup only on recently ingested nodes to catch parallel-ingestion duplicates). Map to our builder: our `has_invariant` edges target 40-char truncated virtual ids (graph.md:17, mag/knowledge_graph.py:165) = the "summaries mistaken for facts / unmerged duplicates" failure mode; our `maps_to` free-text ids (graph.md:18, mag/knowledge_graph.py:172 vs :85) = missing name-vs-identity split; our 300 case_law rows collapsing to one literal id `law:` (graph.md:19, mag/knowledge_graph.py:123) = no alias/canonical layer at all. The Iusztin thresholds give the estate a concrete third discipline the three-fix list does not name: after fixing the writer, add the SAME_AS pending-review edge + tombstone pattern so future id drift lands in a review queue instead of silently dangling.

Corroboration on the X door: @Connected_Data/status/2062482762758504520 (2026-06-04, resolved via fxtwitter) compresses the same pipeline into "entity resolution and deduplication are two distinct decisions" with the same thresholds and the nightly dream pass. @rewind02/status/2084576214463758391 (2026-08-04, 48.4K views, X article "Agentic Knowledge Graphs: what actually works in production", fetched) names the production failure list our graph already exhibits: "unmerged duplicates, relationship-type sprawl, summaries mistaken for facts, misusing per-episode ingestion on static data", and prescribes ID filtering for name disambiguation plus unique constraints at load time (their Neo4j loader carries an ALLOWED_PREDICATES whitelist; our builder hardcodes only two relations, graph.md:9). GAAMA (arXiv:2603.27910, v1 2026-03-29, abstract fetched) names our defect class from the paper side: entity-centric knowledge graphs "suffer from mega-hub effects in conversational data" (our 9 family nodes and the 9-in-edge `invariant:law` hub, graph.md:23-25), and answers with concept-mediated hierarchy + episode preservation, scoring 79.1% mean reward on LoCoMo-10 (+4.2 over tuned RAG).

### Q2. The world-rib lowering contract (laws.md:61) and the cathedral ties (laws.md:70)

The closest published analogue of "what type does a RIB lower to before any renderer is built": GSMem (arXiv:2603.19137, v1 2026-03-19, abstract fetched) lowers agent memory to a re-observable geometric state, 3D Gaussian Splatting as persistent spatial memory with a dual retrieval layer (object-level scene graphs + semantic language fields), and states the design criterion in one line: "existing scene representations, such as discrete scene graphs or static view-based snapshots, lack post-hoc re-observability". Read as a lowering contract: the lowered type must support re-derivation of novel views (renders) from the stored state, which is the same law our ribs already hold, "every emitted world must be re-derivable from its RIB or it is a lying map" (laws.md:62 citing RIB_DEADDROP_FUTURE_SELF_20260811.md:59-67). The deaddrop rib's own sequencing (RIB -> 2D field -> 3D mesh -> world -> code, laws.md:61) matches GSMem's stack (typed scene graph state -> geometry -> render) but no X-thread or paper found this window resolves the two contested cathedral ties (descent order, gate style). Those ties are estate-internal disputes between named prior models; nothing published names them, and I did not find a third-model tiebreak. Filed OWED, not guessed: the sweep's contribution to laws.md:70 is the lowering-contract analogue above, not a tiebreak.

### Q4. Keeping a 350k+ row own-memory corpus queryable without index decay (the B2-465 disease)

Two measured answers, both read this session:

1. **Maintenance scope governs efficiency, not structure.** "Are We Ready For An Agent-Native Memory System?" (arXiv:2606.24775, v1 2026-06-23, html fetched; SJTU/Tsinghua/MemTensor; 12 systems x 5 workloads spanning 11 datasets) measures the exact trade our estate faces (navigable graph vs text search): "efficiency is governed by maintenance scope rather than structure alone" (fetched); localized maintenance beat global reorganization by 30-40x on latency (LightMem 48.3 utility at 3.67s/query vs graph-wide systems at 116-155s for similar utility, fetched); conservative merging beats delayed flushing (delayed flushing drops the same system to 20.6/19.5 Answer-F1/EM, fetched); and "Retaining the original conversational content is more important than increasing abstraction or hierarchy for sustaining both factual recall and reasoning quality" (fetched). For B2-465: incremental delta-only healing with raw content retained is the measured winner; a wholesale restructure is not.

2. **The estate's own stack (SQLite FTS5) is a competitive architecture, not a compromise.** ChronoHybridMem, rank #5 (44.33) on the first Agent Memory Leaderboard cycle (@AgentMemoryL/status/2096799172112556146, 2026-09-07, in-window, fetched): RAW+FACT storage with `source_message_id` traceability, SQLite FTS5 dual-path retrieval, constrained reranking; tweet verbatim: "Agent Memory should return evidence, not just similar text. Raw messages, source-linked facts, dual-path retrieval, and constrained reranking make memory verifiable." Their mechanism is a design steal for our knowledge_graph edges: edges that carry a source row id (source_message_id) are edges that can be integrity-checked against the bytes, the exact instrument our 823/825 census lacked. Overlap note: the ChronoHybridMem headline is already half-held: memory/runs/gapwave/context_economics_1m.md:98 cites "ChronoHybridMem 'evidence, not similar text'" in the verbatim keep/drop context; the leaderboard entry, the FTS5 dual-path detail, and the source-id mechanism are new this sweep.
