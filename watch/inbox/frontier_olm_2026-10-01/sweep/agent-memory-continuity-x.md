## Answers to the four research questions

### Q1. Persistent cross-session memory in frontier/corpus systems, mapped onto rib/residual/registry/leaf

The 30-day window's strongest pattern: published systems are converging on EXACTLY the estate's shape (md-first, append-only, boundary-triggered, human-gated). Dan Kornas's `agent-memory` runtime (2026-09-27, fetched) publishes "Markdown-first store (plain files, greppable/versionable)" as source of truth, BM25 on SQLite with optional vector index, "boundary-triggered writes via hooks at session boundaries," and "sleep-time consolidation, with deletions as proposals for review" - that is the md-record law (lens/laws.md:48), the FTS5 corpus index (AGENTS.md B2-465), the pile habit, and the append law (lens/laws.md:50) re-derived independently. Paul Iusztin's Decode harness (2026-09-08, fetched) splits memory the way the estate splits ribs from residual: hand-written AGENTS.md kept under ~300 lines vs auto-extracted MEMORY.md "appended as dated bullets, capped at 200 lines / 25,000 bytes" - a concrete cap policy for our own auto-extracted memory files. Alpha Batcher's "Agent Memory That Improves Between Runs" (2026-09-03, fetched) proposes a minimal v1 built entirely on files: "an append-only events.jsonl, episodic summaries, facts, and versioned runbooks" (events.jsonl = our steps.jsonl/receipts; versioned runbooks = our ribs), citing Anthropic's Dreams research preview, where "a background job reviews 1-100 sessions against an existing memory store and proposes changes for human approval" (the article's rendering; the promotion-is-human-gated law is lens/laws.md honesty group). The rib/residual/registry/leaf mapping the window supports: registry = Zep's facts (typed, current), residual = thread summaries/episodes, ribs = versioned runbooks/procedures, leaf = observations, biography = user summaries. Akshay's Zep article (2026-09-29, fetched) names six context types: "facts, entities, episodes, thread summaries, observations, user summaries" - a published typed vocabulary the graph lens found our own graph lacks (it has only two relation types, graph.md:11).

### Q2. Relational (entity-relation) memory evaluation methodology

Two instruments, both read this session. (a) The benchmark-integrity genre: S_BatMan's "Mem0 ran its own benchmark. Then it deleted the losing architecture." (2026-07-10, 61,089 views, fetched): Mem0's April 2026 v3 deleted roughly 4,000 lines of graph memory code after its own benchmarks (LoCoMo 71.4 to 92.5, LongMemEval 67.8 to 94.4), while still LOSING the long-horizon BEAM 10M track 48.6 vs Hindsight's 64.1, and a GitHub audit (Issue #4573) found "97.8% junk entries in a production deployment" with feedback-loop amplification as the key critique. The steal for the estate's relational-memory-eval open question (lens/questions.md:106-107) is not the scores, it is the METHOD: report the architecture you deleted alongside the one you kept, and audit the store for junk rate before trusting any score - our SubtleMemory/REL-MEM line (heavily held, 09-30 sweep item 6) gains a junk-rate gate. (b) The split-turn cost finding: Akshay's article preview (fetched verbatim): "Across 15 models and 200,000+ simulated conversations, splitting a task across turns cost 39% accuracy on average; combining the same content into one turn recovered most of it." Any relational-memory eval the estate builds must hold turn-structure constant or it measures the carrier, not the memory - the same turn-2 no-echo defect class descent window 1 paid to heal (lens/burns.md).

### Q3. Memory write policies: what to keep, when to compact, how to invalidate

The record-group laws got published corroboration from four independent systems this window. Harrison Chase on Deep Agents (2026-09-05, fetched, verbatim): "compaction should reduce what is sent to the model, not erase the underlying work history" - oversized tool results written to `/large_tool_results` with only a preview shown to the model, older messages offloaded to `/conversation_history` before summarizing, and a `compact_conversation` tool the agent can fire proactively; this is law 29/30 (chain is ground truth; the window is a reasoning surface, lens/laws.md:51-52) stated as product design, and the linked source is deepagents `middleware/summarization.py` (URL captured in the fetch). Iusztin's compaction policy (2026-09-08, fetched): `/clear`, full LLM compaction at 80% capacity with a summary template (goal, constraints, progress, decisions, next steps, critical context; ~20,000-token tail kept), and LLM-FREE microcompaction at 60% that swaps old tool outputs for placeholders. The measured winner: Towards AI's 11-strategy benchmark in a production AI tutor (2026-08-18, fetched): "full history kept 95% recall vs. 32% for compaction" on DeepSeek across 36 turns, 1.78M tokens processed "97% of those tokens were cached" (prefix caching is what makes keep-everything affordable - the estate's byte-identical cache law is the same bet), and dense retrieval hit 0% recall on deeply buried facts while BM25 held up (supports the FTS5 index choice). Invalidation mechanics: mem0's Dream (blog 2026-08-04, updated 2026-09-28, fetched via non-X door): merge/supersede/synthesize as three background operations; superseded memories "still appear in search by default, because history is often useful. Pass `latest_only=true` to get only current facts"; "Every change is recorded as a state change with a pointer to the newer memory" (nothing deleted; immutable and exclude_from_dream flags honored; weekly per-project schedule; "Add and search latency do not change"). For law 32 (caches must auto-invalidate, lens/laws.md:54) the steal is the lifecycle-state column + replacement pointer + `latest_only` filter: invalidation as an indexed query over append-only records, not a rewrite.
