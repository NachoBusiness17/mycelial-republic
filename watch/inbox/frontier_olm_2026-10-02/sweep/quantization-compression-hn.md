## The four asks, answered from what I actually read

**RQ1 - agentic/task metrics vs perplexity, do the banked laws survive?**
The window's flagship is Quesma's "Benchmarking Qwen3.8 27B quantizations: 4-bit holds up, 1-bit collapses" (HN 49611128, 286 pts / 139 comments, 2026-09-08) - and the estate ALREADY HOLDS it (see dup register). It runs GPQA Diamond + IFBench + Terminal-Bench 2.1 (89 agentic coding tasks, 3h timeout) and never perplexity; the article's own line: "Measuring token prediction differences (KL-divergence, top-1 predictions) is easy, but it does not tell us whether the model gets worse at solving tasks." Delta beyond the held card: Q4_K_M (17 GB) matched BF16 on Terminal-Bench; UD-Q2_K_XL (10.7 GB) dropped noticeably but still scored "at the level of Opus 4.7 or Gemini 3.1 Pro" while writing ~25% more output tokens; 1-bit fell to random-guessing GPQA. **No overturn of the laws.** Nuances the fold should hold: (a) the 2-bit survivor is Unsloth DYNAMIC quants (bits unevenly spent), not flat Q2_K - the "Q2_K never" law is untested against UD-Q2_K_XL-class mixes, worth one measured cell; (b) Q3 was skipped entirely (two commenters flagged the 3-bit hole - the estate's 3-bit floor sits exactly in the untested gap); (c) thread comment kmike84: "KLD computed on agentic traces is much higher, and top-1 % is way lower than if you compute it on chats or wiki text" - independent corroboration that perplexity-style gates are OPTIMISTIC for agentic work, i.e. perplexity-alone-never-gates is right and under-quits. Bartowski's layout-map post is the counter-example shape: its quality metric is KLD on wikitext-2 only, self-acknowledged as not a task metric.

**RQ2 - joint weight+KV quantization and bytes-per-token.**
DeepSeek-V4.1-Flash arch post (zartbot, HN 49735410, 2026-09-17): global KV compressed to **890 B/token** from a 3514 B/token V4-Flash baseline (~4x) via MXFP4 KV (QAT, post-RoPE), 2:1 sequence compression on encoder layers, and cross-layer KV reuse (3 encoder + 1 decoder copies); runtime KV ~1/4 and persistent storage ~1/8 of prior gen. Critical negatives: it is NOT joint weight+KV - backbone weights are not described as quantized; and it ships no task-metric tables (only "high-quality task completion" prose) - another flagship compressing bytes while refusing to gate on anything. Not portable to the estate's llama.cpp/Ollama stack (MLA latent geometry, QAT, RDMA offload). The agentic-kv-cache repo (held since 09-28) adds the serving-side law: on 68,266 replayed Claude Code requests, "under capacity pressure, most recomputation comes from tool-calling loops seconds apart, not from sessions idling past a TTL" - i.e. the estate's constraint is cache CAPACITY not eviction cleverness, and compression/tiering is the named untried lever. **No post-train joint weight+KV result surfaced in the window; that cell stays OWED.**

**RQ3 - one artifact everywhere.**
"Transformers now runs llama.cpp quants" (HF blog, 2026-09-22, HN 49812339) - already held four ways estate-side; fresh read adds the fine print: packed (weights-stay-quantized) path is **MPS-only for now**; dequantize-fallback elsewhere; architecture coverage only Qwen3.5 dense/MoE (+compatible Qwen3.8); no vLLM path; "llama.cpp remains our recommended engine." So the one-artifact answer today: GGUF runs in llama.cpp + Ollama + transformers (Mac packed / elsewhere dequantized); vLLM still forces re-quantization or dequant. Bartowski's per-tensor layout maps (2026-09-10) add a NEW fragmentation seam inside GGUF itself: learned per-tensor mixes vary the bit budget inside a file, and K-quant files must stay IQ-free for compatibility - same extension, different bytes, so "one Q3_K_M" is no longer one thing across quantizers.

**RQ4 - agent memory estate compression as first-class problem.**
Nothing in the window compresses a behavior-row estate's byte mass as its object. Jev-Mem (arXiv 2609.23986, 2026-09-21) attacks memory-op LATENCY (System-One controller off the generation critical path; LoCoMo 0.777, +11.0% rel, 6.6x faster construction) - speed, not bytes; abstract describes no compression/forgetting. Past.dev (2026-09-30) scales recall to 10M-token histories at 85.03% (next published: 68.0%) but on its own benchmark and never describes storage, compression, or retirement; its own weakness row (multi-session reasoning 28.17% at 10M) is the honest part. The estate's biography-mass problem (hundreds of thousands of behavior rows) remains unserved by the frontier this window.
