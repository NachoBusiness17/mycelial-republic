Long chats with Claude eventually get compacted, and every time it happens I lose detail: decisions we made, file names, where we left off.  
  
 first idea was to have Claude write a handoff .md file right before compaction. The problem is the agent can't reliably tell when compaction is about to happen, so a handoff written "just in time" is often late or slightly out of date.

My

So here's my workaround: don't wait for compaction at all. Tell the agent to update the handoff file after every single response. Whenever compaction hits, the latest state is already saved.

This is the instruction I'm testing:

>After every response, create or update a file called HANDOFF.md in the working folder. Keep it short and current. Include: the goal of this chat, decisions made so far, files created or changed, open questions, and the exact next step. Overwrite outdated information instead of appending a full transcript. If the chat is compacted or I start a new chat, read HANDOFF.md first before doing anything else.

Questions for the community:

1. Has anyone set this up, and does the agent actually stick to it over a long session?
2. Is there a cleaner way to trigger a save right before compaction?
3. Does updating a file every turn slow things down or burn through usage noticeably?

Would love to hear what's working for you.

Note: I have it overwrite instead of append, since a file that logs every turn grows large and becomes its own context problem. I know Claude Code has a PreCompact hook, but I'm looking for something that also works in regular chats.

  [PilDog | 2026-09-30 23:07 | score 4] English isn’t my first language, so I used AI to help translate this. Please excuse any awkward wording.

I ran into the same problem and ended up taking a slightly different approach.

Instead of trying to preserve the AI’s memory between sessions, I moved the important project state outside the conversation.

I keep the project documentation structured so that it contains the current state, decisions, responsibilities, rules, and references to the relevant files. Then I give the AI a small entry point that tells it what to read for a particular kind of task.

The important part is that the AI doesn’t load the entire project history or all of the documentation every time. It follows a reading path and loads only the pieces needed for the current task.

So when I start a completely new session, I don’t really need the previous agent to create a perfect summary. The new agent starts from the project state, follows the relevant references, and reconstructs the context it needs.

I also separate “what something means” from “what is responsible for it.” That turned out to be important because otherwise summaries gradually become another source of truth and start drifting from the actual project.

The basic idea is:

conversation memory → disposable
project state → persistent
decisions/rules → explicit
task context → loaded on demand

It took some work to structure the documentation this way, but now I can switch between different AI models or start a fresh session without depending very much on the previous conversation.

Your HANDOFF.md idea is actually a good first step in the same direction. The biggest improvement for me came when I stopped treating the handoff itself as the memory and started treating it as a pointer to the authoritative project state.

      [PilDog | 2026-09-30 23:59 | score 6] Glad it helped! Your Obsidian plan sounds like a good start. Here's how I do it, in case it's useful as a reference.

My setup is just plain Markdown files inside each project's Git repository, next to the code. Coding agents like Claude Code and Codex automatically read an `AGENTS.md` (or `CLAUDE.md`) file in the repo root. So that file is my "start here" note, and it works the same no matter which AI I use.

**1. Built by hand or by the AI?**

Both, and it grew over time. I started with a few simple notes. Every time the AI got confused or made a wrong assumption, I added a rule so it wouldn't happen again. Almost every rule I have exists because something went wrong once.

Now the AI writes and updates most of the files. But there is one important rule: **an edit by the AI is only a proposal.** The flow is:

> AI edits the files → I review the diff → I approve → commit

Only committed content counts as the real project state. The AI isn't allowed to commit without my confirmation, and it never pushes. Pushing is my job. This way an AI mistake can't quietly become permanent memory, and every change is in the history if I need to check or undo it.

**2. Decisions in each project note, or a separate file?**

I keep three kinds of files separate:

- **Rules:** what the AI must or must not do. Each rule has an ID like `PROJECT-GIT-001`, so notes can reference it instead of copying it.
- **Decisions and reviews:** what we decided and why. These go in a separate folder with one file per topic.
- **Current state:** the code, configs and status files themselves.

The most important principle is that **every fact lives in exactly one place.** A decision note says what and why, and links to where the current state lives. When I let copies or AI-written summaries exist, they slowly drifted and started contradicting the originals, and then the AI didn't know which one to believe.

**3. What my entry point looks like**

The root `AGENTS.md` is tiny. It only says where to start:

```markdown
# Agent Instructions

Before any work, read these two files in order:
1. `rules/shared/entry.md`   (rules shared by all my projects)
2. `rules/project/entry.md`  (rules for this project only)

Apply both together.
If a required file can't be read, or two rules conflict:
make no changes and report to me.
```

Each `entry.md` is a map. It says what to read for **every** task and what to read **only for certain tasks**:

```markdown
# Project Rule Entry

## Read for every task
- `structure.md`: what lives where in this repo
- `authority.md`: what you may change without asking me
- `language.md`: which language to use for docs and reports

## Read only when the task needs it
- `git.md`: committing, branches, pushing
- `release.md`: versions and tags
- `deploy.md`: anything touching the servers
- `ssh-access.md`: SSH keys and remote access

If a task covers several topics, read all of them.
If you're not sure whether a topic applies, read it.
```

A few things I learned along the way:

- **Keep the "every task" list small.** At one point my always-read rules were so long that they cost more tokens than the actual work on small tasks. Rules that matter only for specific tasks, like deployment or SSH, belong in the second list.
- **Don't replace rules with a summary.** I once tried a short cheat-sheet of all the rules. Summarizing dropped the exceptions, so the AI started behaving differently than the real rules said.
- **Share common rules across projects.** Rules that apply everywhere, like Git safety or when to ask me first, live in one shared set that I version with Git tags. Each project uses a specific version and updates on purpose, not by accident.

The question that helped me most was:

> "What's the smallest amount the AI needs to read to find the rest on its own?"

Your Obsidian idea can follow the same pattern. A vault is also just Markdown files, so you can put it under Git and use a "start here" note as the map. I'd just keep the always-read part small and commit from day one.
