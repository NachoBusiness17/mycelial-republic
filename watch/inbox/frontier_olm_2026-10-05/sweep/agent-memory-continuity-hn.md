## Pass 2 (deep reads, end to end, this session)

1. **"Agents don't need memory, they need documentation"** (HN 49945933, 368 pts / 271 comments, 2026-10-03, liao.gg). The thread's verdict splits: kaydub "The code IS the documentation" vs hosh "Code as documentation works better when the code is declarative or a DSL". The transferable mechanisms: (a) crazygringo's staleness cure, instruct the agent to be "always aggressive in maintaining current state only, always replace rather than append" (our zknot LATEST.md rewrite-at-logon is exactly this shape; it beat append-only in this thread's testimony); (b) Garlef's deterministic-feedback proposal, lint rules whose error messages coach the agent: "agents need deterministic feedback more than documentation" (direct precedent for our ratchet/citation-lint hooks as memory-enforcement, not just code-enforcement); (c) nijave's lifecycle critique: the article's memory design "ignores the lifecycle involved with memory" (no time, no reconciliation, no preference-vs-fact split, concurrent agents corrupt a single store). All three bear on Q2/Q4.

2. **Motif, experience graph over coding-agent history** (HN 49877499, 2026-09-28; repo github.com/motif-Labs/motif read in full). This is the strongest published Q2 design: session records welded to the code that produced them. `motif blame src/limiter.ts` "returns the sessions that produced this file, freshest first", each hit "names the person, the tool, the session"; sessions carry short-hash ids (`claude-code:88b19192`, `codex:99bfccc0`); entity identity is grounded by corroboration, not free text: node confidence, "corroboration and a human's vouch raise it; conflict, staleness and age lower it"; contradictions "flagged instead of quietly piling up"; notes whose source files were reworked are "marked possibly stale" and queue for human review (admit/reject/prefer/confirm/retire); "Rulings never delete"; readers "parse tolerantly and never fail a whole sync on an unknown shape". Bench: 1.77M tokens of real history, "recall answers 8 of 9 questions inside a 1,500-token budget". This is the anti-phantom kit for mag/knowledge_graph.py:236-239: identity comes from observed tool-session events plus confidence decay, not `Path(str(m)).name` slicing of free text.

3. **OKF Agent Memory thread** (HN 49581240, 81/32, 2026-09-05; git-native Open Knowledge Format store). The comments are the signal: vshulcz ran a cold-start benchmark over 19k LongMemEval sessions and found "The funny thing is BM25 basically ties embeddings here at 1/100th the cost. The real cliff is reranking... and staleness." plus "Vector search has zero concept of 'superseded info'". glub: "precision/recall is relatively 'solved'. What nobody has gotten close to solving is maintenance and provenance." olenzma: "Invalidation is not an algorithm, but a judgment made in context." langs's challenge ("Why benchmark the latency instead of recall/precision?") is the exact eval-gap question for our graph lens. Q1/Q3 relevant: provenance tiers (human-verified vs agent-generated) as the identity anchor.

4. **past.dev on BEAM** (HN 49923182, 2026-10-01; blog past.dev/blog/introducing-past-dev read in full). Q3 eval design, published at ICLR 2026: BEAM "asks 2,000 questions about 100 long conversations at four lengths, from 100K to 10M tokens", grading ten abilities including "event ordering to contradiction resolution". Their 85.03% at 10M: "Across a hundredfold increase in history it loses 7.05 points, and the next published system at 10M scores 68.0%" (vendor-published, mixed configs). Recall returns "the verbatim excerpt, its date and the id of the source record"; deleting a source record "removes the memory derived from it" (provenance-keyed retirement). Admitted weak spots are the interesting part for a biography shelf: multi-session reasoning "falls to 28.17% at 10M", contradiction resolution 73-79%. LoCoMo comparison table included (93.12% vs mem0 92.5%, Hindsight 92.0%) with a disclosed "community-corrected answer key" caveat.

5. **CTWM: heavy-tailed memory traces** (HN 49955466, 2026-10-04; redreamality.com blog, arXiv:2610.00010). Q3/Q4: "finite agent memory reliably concentrates into a small core and a long tail, but the meaning of that tail depends on the driver"; "finite top-(k) retrieval can create hub-like memory concentration before any semantic policy enters the loop". Mechanism: budget by access rank b(r) proportional to r^(-tau), keep a summarized tail, never retrain. Eval discipline transfers directly: audit visit counts and bottom-half tail error, check concentration collapses when retrieval is disabled (Gini drops 33-45% in the write-only control, i.e. hubs can be an artifact), report paired token reductions before success claims, separate allocation KPIs from serialization KPIs. LongMemEval: -24.48% tokens at parity, with a multi-session recall blind spot as the known cost.

6. **Four Kinds of Agent Memory** (HN 49628820, 2026-09-09; memanto.ai blog read in full). Q4 taxonomy: working (context+scratchpad), episodic (time-anchored), semantic (distilled claims), procedural (weights/tools/rules). Core claim: "The episode goes in, a claim comes out, and something has to perform that reduction", and "A vector store full of conversation chunks is not semantic memory. It is episodic memory with better search." Procedural self-editing risk: "The agent is grading its own homework, in the file that determines its behavior." Retention lifetimes follow world-change rate, not cognitive type; expired memories keep content plus expired_at/expired_by and are restorable; every memory carries a provenance enum (explicit_statement/inferred/corrected/validated/observed/imported) plus confidence. Maps 1:1 onto our stack: ribs=procedural, zknot recap=episodic boundary, catalog=semantic candidate; what we lack is the named distillation step (812 observations to 2 memories as their ratio benchmark).

7. **Aura, temporal graph memory** (HN 49951895, 2026-10-04; repo github.com/chetto1983/Aura README read). Q1-adjacent: facts stored alongside "sources and validity windows"; temporal paths "return supporting evidence" so answers come back with provenance; one isolated database per user identity "enforced by the server". Honest gap: the README documents NO entity-resolution mechanics. It shows validity windows and provenance but not how entity ids stay stable. Useful as the counter-example: temporal validity without identity resolution still leaves the weld problem open.
