## Research question answers

**RQ1 (do vLLM-class advances apply to a Windows ollama janitor fleet?):** Only through WSL2, and only if concurrent batching is the bottleneck. vLLM has no native Windows support (issue #669: "We currently do not support Windows. However, vLLM should support Windows WSL 2."). Issue #37242 proves the WSL2 path now delivers CUDA graphs on Blackwell (WSL2 2.7.0+): ~140 tok/s vs Ollama ~111 tok/s on Qwen3-14B (about +26 percent), but WSL2 reaches only about 70 percent of bare-metal Linux (180 to 200 tok/s). Against that, allenkuo's RTX PRO 6000 Windows measurements show Ollama WINS the metrics a single-stream agent fleet feels (decode 134 vs 89 tok/s, TTFT 33 vs 129 ms) while vLLM wins prefill and concurrency (c4 341.8 vs 123.5 tok/s). For gemma:2b scut janitors, Ollama's TTFT and zero-WSL2 ops cost dominate; vLLM becomes right only when many concurrent requests batch up. The quant A/B tie at ceiling stays banked and instrument-scoped (not re-run, per the ask); these outside numbers give the regrade direction without touching it.

**RQ2 (thinking on/off economics, laws lens q10):** Outside evidence supports REGRADING the suspect rows toward confirmed, on two legs. (a) Nous Research measured open-weight models using 1.5 to 4x more tokens than closed ones, up to 10x on simple knowledge questions: open models overthink exactly the janitor-class work the estate runs, so thinking-off as the local default is externally corroborated, and the explicit off-switch discipline (only `thinking: {"type": "disabled"}` is the off state, per `memory/rib/RIB_INFERENCE_BUDGET_20261001.md:126-128`) matches how the field controls it. (b) Mem0's Sep 2026 test: high-effort GPT-5 mini burned 9,651 output tokens on average for a single question ($0.0193); injecting memory instead of full history cut output tokens 8.5x at equal judge quality. Lesson for the estate: context compression attacks the same burn the off-switch does, without degrading the judgment tier. EMPTY_REASONING burns remain terminal and were not refired (law 8 honored).

**RQ3 (which throughput claims survive instruments-only on one consumer Windows host):** Reproducible class: 140 tok/s vLLM / 111 tok/s Ollama / 17 tok/s enforce-eager on Qwen3-14B AWQ, RTX 5090 + WSL2 (issue #37242, llama-bench-shaped, one box); 134 vs 89 tok/s decode and 33 vs 129 ms TTFT on RTX PRO 6000 (allenkuo, OpenAI-compat endpoint instruments). NOT reproducible on a consumer host: data4sci's DGX Spark GB10 numbers (284 tok/s is a batch-256 aggregate on 128 GB unified memory at 273 GB/s; the box is not consumer), Red Hat's 793 TPS concurrent-serving figure, and uzu's 1221 tok/s (Apple M5 Max, and the engine is Apple-only). Any banked claim must name box + batch shape or it dies at the instrument.

**RQ4 (can standing-wave GB/day absorb a serving stack?):** Serving forces a NEW budget class, it does not fold into the existing one. vLLM's tiered KV offloading writes evicted KV to filesystem and object-storage secondary tiers BY DESIGN ("preserves evicted KV data across host memory, storage, and remote peers"), so served tokens become disk a second time after the weights: law 16 (tokens are disk) extends to a KV-tier surface with its own growth rate. HiSparse similarly pins multi-hundred-GiB host DRAM pools (384 GiB + 128 GiB split on 8x H200). Counterweight: v0.31.0's `vllm preload` weight-cache daemon keeps post-quantized weights GPU-resident across restarts (restart cost stops re-paying disk/quant time), and `--enforce-eager` now also disables JIT warmup. If a serving stack ever lands, smith's DISK ETA alert needs the KV tier path added; until then the fleet's serving surface is Ollama, which does not carry this class.
