## Find 1: TAK, Task Aware Knapsack quantization (r/LocalLLaMA, posted 2026-09-07)

**The steal as a mechanism.** TAK ("Task Aware Knapsack", author devildip / ByteOtter) is a weight-quantization pipeline that allocates precision by task value instead of uniformly. Live-verified pipeline, in the author's words: "It starts with an imatrix built from a task specific corpus. Then we find the model cliff at is smallest size before complete collapse. It then combines those measurements with tensor level allocation promoting and demoting tensors within a byte specific budget" (sic; typo in original). Four portable steps: (1) build an importance matrix from a task-specific calibration corpus, (2) find the model cliff, the smallest size before complete collapse, (3) knapsack promote/demote tensors under a hard byte budget, (4) evaluate on a held-out set ("These are all tested on a held out dataset"). No pruning, fine-tuning, or merging: "purely an Imatrix + damage allocation process." Scores from the post body: Qwen3.8-27B TAK 82.81% reasoning vs 77.34% for the byte-matched Unsloth UD IQ2_S (+5.47) and 83.59% for BF16, i.e. 99% of full precision at 15% of the size (the title's claim). The same pipeline beats matched Unsloth by +11.72 on Qwen3.5-4B, +14.06 on Gemma 4 E4B, +19.53 on Gemma 3 4B QAT.

**The failure mode is the second steal.** The post edit and thread confirm domain lock: users hit repetition loops in coding, and the author states "Coding was not part of the protected set of tensors and outside its domain" and "it doesn't hold up for coding. This is domain specific for reasoning." The calibration corpus is small and benchmark-derived: "a 192 set of calibration items taken from benchmarks and custom reformatted into answer only formats." Most instructive: an earlier coding-corpus attempt "kept improving math as a baseline instead of the target," meaning a mis-aimed importance corpus silently optimizes the wrong objective. So the shape is: task-aware allocation wins big in-domain, degrades out-of-domain, and the size of the win is bounded by corpus aim, not corpus size. A thread skeptic's compression of the same point: "task-aware = benchmax-aware," which the author concedes is fair while pointing at the held-out sets as the control.

**Why it lands here.** The estate does not train weight quants, but it runs the identical allocation problem at two other layers, both currently signal-blind (see Estate map). Resonance noted, not load-bearing: AGENTS.md:32 names qwen3.8-max-prime as the funded workhorse tier, and the TAK post quantizes the same Qwen 3.8 family at 27B locally; the post's GGUFs (huggingface.co/ByteOtter) are irrelevant to the funded API lane and were not fetched.

## Find 2: "How to Make Tool-Using LLM Agents Efficient? A Survey" (Preprints 202608.0365, 2026-08-06, DOI 10.20944/preprints202608.0365.v1, Yunuo Hu et al., non-peer-reviewed)

**The steal as a mechanism.** A taxonomy of 111 works (count verified in Appendix C.2, coverage through July 2026) along four agent-loop stages: Efficient Tool Context (tool set compression, tool description compression, history compression), Efficient Tool Calling (eligibility-aware, cost-aware), Efficient Tool Reasoning (trajectory optimization, reasoning reuse), Efficient Tool Execution (results caching, parallel execution, speculative execution). Appendix D Table A4 pairs each stage with its primary resource (context tokens, call count, trajectory length, end-to-end latency) and its characteristic risk, e.g. for Context: "Compression may remove latent tool dependencies, execution-critical schema constraints, or historical evidence needed for later grounding and recovery."

**The scoping evidence.** The survey excludes Find 1's territory on purpose, which is direct evidence the literature separates weight quantization from agent-loop efficiency. Limitations: "our scope focuses on agent-level overhead induced by tool interaction and excludes generic LLM inference, compression, and serving optimizations." Appendix C.1 eligibility is stricter: "We also exclude works whose efficiency gains are not tied to tool use, including general LLM inference acceleration, model compression, serving optimization, and generic system scheduling." The estate should hold the same line between its quantizer organ and its context organs instead of letting "compression" blur them.

**The interlock.** Section 3.1's Rethink block names the exact gap TAK fixes for weights, transposed to context: existing context-compression methods are mostly training-free and "rely on generic relevance signals," so they may miss latent associations between task and context and prematurely discard useful components (paraphrase; the Rethink block of 3.1.3). Generic relevance is precisely what the estate's compile law uses today: "weight = recency x shape" (tools/thought_quantizer.py:18-19). TAK's task-corpus importance, knapsack under budget, and held-out battery is the fix, applied at the instruction layer instead of the tensor layer. The two finds are one lesson at two layers.

Arm 2: same 374 kept laws re-ranked by knapsack value = graded-outcome co-occurrence lift from the trail/behavioral ledges, top-12 flash under the SAME character budget (byte-matched, exactly TAK's control against Unsloth).
