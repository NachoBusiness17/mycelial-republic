### Q2. Published CRD or merge-friendly log design for knot multi-writer safety (knot-as-CRD)?

This run found TWO published, deployed shapes the predecessor's Orly half was pointing at: (1) Loro/Lody's production sync engine (leon7hao article, Sep 22, talk transcript): the backend moved to ElectricSQL's Durable Streams protocol, "each stream is an append-only log with offsets, which is all CRDTs need since peers converge with the same update set" (fetch rendering), with client snapshots, a bootstrap protocol, ephemeral channels, append-CAS for end-to-end encryption, and Raft groups per stream. The talk's honest open problem is the knot's open problem: cross-stream transactions - one user action touching two streams has no transactional guarantee, and per the speaker it is "不是再加一个 CRDT 就能解决的" (not something adding another CRDT can solve). (2) 0xlelouch_'s Sep 4 design: doc_versions (snapshot every N ops) + doc_ops (append-only log) + idempotency by (client_id, op_id) + pinning each hot doc to a single writer to serialize ops, leader rebuilt from snapshot + op log replay on crash. Estate reading: single-stream append-only + deterministic fold is now twice-published peer practice (matches the estate's stateless-pure-transform law); CROSS-STREAM transactions are unsolved in the peer literature too, so knot-as-CRD should scope itself to per-lane append + fold and treat cross-knot transactions as open, not as a missing feature.
