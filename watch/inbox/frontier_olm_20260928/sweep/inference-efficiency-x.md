## RQ1: current speculative/consensus decoding for small local models; does any published design answer Q1?

Findings, strongest first, all read this session:

1. **Inference-Time Consensus for Mitigating Hidden Behaviors**, Narang, Tajdini, Zhang, Morgenstern (UW), arxiv 2607.23394v1, 25 Jul 2026. Read end to end. Two consensus decoders operating IN the actual token output space (vocabulary logits, autoregressive): token-wise minimum (pi_min, every reference caps a token's raw score) and base-relative minimum (pi_delta, apply the smallest unanimous change else revert to base), with quorum aggregation and semantic smoothing as extensions. This is the first published design I found whose decode mechanism is what Q1 asks for (task-output-space, not surrogate domains). Three estate-critical caveats from the same read: (a) cost is "every generated token requires one forward pass through each reference model" plus rollout/embedding calls for smoothing; (b) the evaluated benefits are synthetic (joke markers, hidden animal preferences), the authors concede it "does not show that consensus preserves broad capabilities"; (c) the headline law is "Consensus measures support, not correctness." (d) coordinated sources can manufacture agreement; "Preventing that failure requires meaningful data provenance outside the decoder." VERDICT vs Q1: the mechanism exists now (logit-space consensus with quorum), but the redesign the rib wants (consensus that RAISES task correctness for grounded workloads) remains unpublished; if anything this paper independently confirms the rib's empirical result RIB_MINDSWEAVE_EVAL_CONSENSUS_ILLUSION (flock consensus wrong 3/3 at strength 0.60-0.67) from theory: support is not correctness, so high consensus strength is evidence of nothing.
2. **LK Losses: Direct Acceptance Rate Optimization for Speculative Decoding**, Samarin et al. (Nebius/Skoltech), arxiv 2602.23881v2, submitted 2026-02-27, revised 2026-06-01, ICML 2026. Read abstract page end to end. Key mechanism: KL divergence and acceptance rate share a global optimum but capacity-limited SMALL draft models settle where minimizing KL does not maximize acceptance; LK losses optimize acceptance directly; 4 draft architectures x 6 targets from 8B to 685B; gains up to 8-10 percent average acceptance length; "LK losses are easy to implement, introduce no computational overhead". This is the direct spec-decode lever for the estate's small local janitors: train (or pick) drafts by acceptance, not KL.
3. **BV Loss: Block Verification-Aware Loss for Block Diffusion Speculative Decoding**, Kim et al., arxiv 2609.34832v1, published 2026-09-28 (same day as the stamp). Surfaced via the LK Losses arxiv API query; abstract sentence read: "BV loss also outperforms tokenwise acceptance objectives such as TV loss and LK loss". Not deep-read (abstract only via API); banked as the freshest evidence the acceptance-objective line is moving weekly.
4. **carteakey.dev "Local LLM Inference Optimization: The Complete Guide"** (v dated 2026-06-12, updated 2026-08-14, first published 2026-04-04). Read end to end. The measured spec-decode numbers on a single consumer RTX 4070 (Linux/CachyOS): Gemma 4 26B baseline 38.5 tok/s, 100.60 tok/s with QAT+MTP (2.6x); Gemma 4 12B 120.80 tok/s with QAT+MTP (2.0x); MTP draft lengths swept per model (2 for 26B, 4 for 12B; upstream default max is 3). The interaction law the estate must not learn the hard way: quantizing the TARGET KV cache to q8_0 "drove draft acceptance close to zero" on Gemma 4, while f16 KV kept acceptance above 70 percent and was faster end to end despite more VRAM. This cross-corroborates the sibling lane's QuixiAI finding (turboquant KV quant destroyed multi-turn tracking): two independent sources now say KV precision is the spec-decode and multi-turn killer, not weight quant.

VERDICT RQ1: current scheme for small local models is draft-and-verify with MTP or trained drafts, acceptance-rate-optimized (LK/BV losses 2026), 2.0-2.6x measured on Gemma 4 class at RTX 4070 scale, gated on f16 KV. A published consensus-decode redesign in the Q1 sense does NOT exist yet; the nearest published object (2607.23394) proves the mechanism class and simultaneously proves why it fails as a correctness device.

## RQ4: activity/energy profiling mapping cool vs heat per lane; a tool without kernel drivers?

1. **PowerJoular** (github.com/joular/powerjoular, GPL-3.0-only, Adel Noureddine, repo page copyright 2020-2026). Read end to end. Monitors CPU and GPU power with BOTH per-PID (`-p pid`) and per-application (`-a appName`, covering all its processes) attribution on Windows/Linux/macOS. Windows paths, from the README: CPU RAPL via the Windows Energy Meter Interface (EMI) with "nothing to install" and no special privileges or drivers needed (EMI tried first, then PawnIO, then Hubblo's RAPL driver; overridable via JOULARCORE_WINDOWS_RAPL); Nvidia GPU via NVML (ships with the driver), AMD via ADLX (ships with the AMD driver). "Low overhead: written in Ada, compiled to native code, one binary with nothing to install alongside it." This is the closest off-the-shelf answer found to the Q7 sensor question: a no-driver, no-admin Windows energy profiler with per-app attribution, cron-able per lane.
2. Honest limits of that answer: NVML exposes DEVICE-level watts, not per-process watts; per-process GPU energy still has to be apportioned by utilization share (the README does not claim per-process GPU watts). EMI covers CPU RAPL domains. So PowerJoular closes the "is there a no-driver tool" sub-question (yes, for CPU-side per-app watts plus device-level GPU draw) but not per-process GPU joules. Q7 itself is a living per-lane/per-time-of-day map and stays open by construction; the sensor now has a named candidate.
3. The unverified snippet about an arxiv paper claiming nvidia-smi samples power for only ~25 percent of runtime with energy errors up to 65 percent on A100: never located at a URL (arxiv API returned 0 entries), snippet-only, NOT banked as fact; flagged as OWED because it would calibrate any NVML-sampling design the estate builds.
