## Findings per research question

### RQ1. Do 2-4 bit weight quants preserve tool-call JSON reliability for 2B-8B models, and which formats for Ollama-class serving?

**Direct evidence on tool-call JSON vs quant level: none found in this sweep.** The strongest quant eval on HN in the window (Quesma, 286 pts) tests Qwen3.8 27B GGUF (Unsloth Q8_0 / Q4_K_M / UD-Q2_K_XL / UD-IQ1_S) on llama.cpp with GPQA Diamond, IFBench, and Terminal-Bench 2.1, and the fetch states plainly: "there is no dedicated tool-calling, function-calling, or JSON-output benchmark." So the headline survives at the honest grain: agentic competence is measured (Terminal-Bench 2.1, agentic coding, 89 tasks), JSON-validity under quantization is not, at least not on HN's front page in the last 30 days. Verbatim anchors from the blog: "Yet the 17 GB Q4_K_M matches the full model on a popular agentic coding benchmark, Terminal-Bench 2.1."; "there is no change between models, down to a decent 2-bit one" (IFBench, strict instruction following); "At 1 bit, the model performs around random chance on GPQA Diamond." Thread adds the practitioner caveats: kouteiheika "these quants are not quantized uniformly, so 4-bit isn't actually a 'true' 4-bit here"; anyfoo saw a personal benchmark die at Q5 and recover only at Q6_K_XL; kmike84 + stared agreed KL-divergence "didn't differ on wikitext or Linux kernel code" but is "dramatically different, depending on which dataset you use," with agentic traces diverging far worse; skolos reports NVFP4 weights plus KV cache at q4 running coding agents to 200k context without noticeable degradation.

**Formats favored for Ollama-class serving:** the whole window speaks GGUF-on-llama.cpp (Ollama is a llama.cpp consumer): Unsloth dynamic quants (Q4_K_M as the default rung, UD-Q2_K_XL as the small rung), plus bartowski's new per-tensor layout maps that make lower tiers honest again: "token_embd dominates the sensitivity scale," "attn_v, attn_output, ffn_up, and ssm_out are extreme standouts on sensitivity," with _S/_M/_L naming rules restored and a KLD-per-bit canary gate. Transformers now also runs llama.cpp quants directly (HF blog, 2 posts). For tool-call JSON specifically the mitigation pattern in the window is constrained decoding decoupled from weight quality: XGrammar-2 (MLC, "Fast, Customizable Structured Generation for Tool Calling and Agents", surfaced only, not deep-read) and Willison's llama-cpp-python grammars TIL (surfaced only). The seangoedecke post adds the cheapest trick: prefill the response prefix and generate one constrained token, tested on Qwen2.5-1.5B-Instruct with "a 2x-3x speedup compared to non-prefixed structured output."

**Estate read:** for janitor-tier (gemma:2b / gemma4 per AGENTS.md) the transfer is: stay at Q4_K_M or above, prefer imatrix/layout-map GGUFs, and enforce JSON with grammars rather than trusting the quant; the 2B class is below every model actually benched in this window (27B, 9B, 14MB Jev-class), so published evidence does not reach down to the estate's smallest tiers. OWED: no published eval found that benches tool-call JSON validity as a function of quant level for 2B-8B models (BFCL-style); the BFCL leaderboard thread is from 2024 and not deep-read.

### RQ2. Does the literature distinguish quantizing weights from compressing instructions, and does it support the estate's inflated-echo finding?

**Yes, the literature keeps them on different axes, and the distinction is three-fold:** (a) weight quantization is post-hoc numeric compression of trained parameters (Quesma, bartowski, GGUF ladder posts); (b) instruction/prompt compression is text- or soft-token-level and needs either a task-anchored judge (LLMLingua's small aligned LM) or training (Gist tokens, arXiv 2304.08467, which compresses instructions into learned virtual tokens via fine-tuning; forced context distillation, jx0.ca, which bakes context into weights by training); (c) KV/cache-level compression (RQ3) compresses activations, not text. HN itself separates them: the 30-day window has zero prompt-compression stories (nbHits 0) while quantization and KV compression front-page repeatedly; prompt compression lives in 2023-2026-03 threads.

**On the estate's finding** (all 24 rows of memory/corpus/quantized_thought/instructions_frontier.jsonl carry `count_verdict: "inflated echo - provenance only"` per watch/inbox/frontier_olm_20260928/lens/laws.md:5, and compile_report.json shows 37 of 307 kept rows are error-quoting laws plus 3 shell-error echoes per lens laws.md:60): the LLMLingua thread is the closest public replication of the failure mode. The thread's most useful comment (TarqDirtyToMe) says the tool is meant for instructions, system prompts, and memory with a defined task, not raw context-free text, where the small model has "not enough information to judge" what matters; refulgentis notes the demo reduces a 5-shot prompt to "one or two very brief examples without reasoning"; compressed-thread experiments failed at 13.2x when GPT-4 could not parse the result. That is: unanchored textual compression of instructions degrades exactly the way the estate's compiler found (echo without decision weight). The estate's compiler is itself the honest version of this literature: it refuses fragments and telemetry (compile_report.json: refused_telemetry 2, refused_fragments 9), marks everything provenance-only, and keeps the real law in the ribs. ### RQ4. SOTA prompt compression vs the deliberate-ask context tax

**The deliberate-ask shape is already the winning design, and the window's evidence says do not lossy-compress it.** The shape (frozen prefix, cache-shared + tight ask ~207 chars + output contract, instructions_frontier.jsonl:1 and watch/inbox/frontier_olm_20260928/lens/laws.md:18, measured cache hit-ratio 6.5% -> 98% and cost ~$161 -> $3.60 per RIB_SELF_MY_EFFICIENCY.md:5-8 as cited there) is a prefix-caching design. The window's strongest results (DeepSeek prefill halving, agentic-kv-cache prefix policy work, vLLM prefix-cache warming) all compress recompute, not text: they keep the bytes byte-stable and make the second touch cheap. Lossy text compression (LLMLingua family) would actively break that: it rewrites the prefix, killing cache identity, and the practitioner thread documents cross-LLM fragility (MrYellowP: compressed prompts "wouldn't necessarily work for different LLMs easily"). Gist tokens require per-model fine-tuning, out of reach for Ollama-class janitors. The estate's own context_compression organ already encodes the correct invariants (memory/knowledge_graph.json module:context_compression.py): "Never lose sovereignty information. Compress form, not substance.", "A/B test every compressed prompt before deploying.", "Keep the original as fallback. Compression is optimization, not replacement." Recommendation, grounded in the fetched pages: spend the effort on the frozen prefix (content-addressed, byte-stable RIB) and the mag/context_pack.py offload lane (mag/context_pack.py:15-16, VALID_PACK_MODES + PACK_OFFLOAD_FILE), compress only the variable tail, and treat any new text-compression claim as subject to the RQ3 catalog-retention harness before adoption.
