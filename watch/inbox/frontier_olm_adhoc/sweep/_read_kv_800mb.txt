    I work on Atomic Agent, an open-source agent built for local models first, so weigh this accordingly. We just shipped the first desktop build. This post is about what's under it, because most agents are designed around a frontier cloud model and then "support" local ones, and we tried to go the other way. Here's what changed once we treated a 4B to 9B model as the main target. The KV cache is compressed. We ship our own llama.cpp build with TurboQuant, set to turbo3 by default. In our tests on a MacBook Pro M5, a 128K chat on Qwen 3.5 4B fits in 800 MB instead of 4 GB. It's lossy, so expect a small quality hit in exchange for the memory. The prompt prefix never changes mid-session. System prompt, tool catalog and skill list stay byte-identical between steps. Memory writes and anything that changes per step go at the tail. That lets llama.cpp reuse the KV cache for everything it already processed. On the same M5, a reply on Qwen 27B that used to take 4 min 20 s to start now starts in about 1 s. That's cache reuse, not faster inference, but on a long session it's most of the wait. State lives outside the model. Session state, memory and old tool results sit on disk, and the prompt is a bounded slice of them. On local models, long tool output gets trimmed before it reaches the context.
