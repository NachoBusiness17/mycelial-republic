    Thanks, the 2048 profile is hilariously close to the edge. 1792 is what I’d recommend if you want any practical headroom; 2048 was mainly about proving the full 131K KV + Vision configuration could actually coexist on the 16GB card. The Q4 KV path isn’t from KTransformers. It’s a fork-specific implementation built on top of NInfer’s existing paged KV and GQA attention machinery. The cache codec is signed symmetric INT4-G64 . For each token/KV head the 256 d head is split into four 64 value groups, with an FP16 scale per group. Scale is absmax / 7 , codes are clamped to [-7,7] , and two signed 4-bit values are packed per byte. The important part is that quant/dequant isn’t implemented as a separate pass. It’s fused into the attention path. On decode, newly generated K/V rows are quantized directly into the paged Q4 cache. When attending: Q is quantized on chip to INT8 per 64 d group packed Q4 K is unpacked into INT8 staging and QK uses the existing s8 tensor core path the group scales are applied to the QK accumulators packed Q4 V is unpacked/dequantized into BF16 for the PV stage There’s also a specialized packed K/V async staging path for the T=4 decode case so it can move the compressed representation through memory before unpacking it in shared memory. Prefill has its own Q4 fill/attention kernels as well, so the cache stays Q4 throughout rather than being expanded to BF16 somewhere in between. The underlying page system is NInfer’s paged KV design 64-token pages/block tab
