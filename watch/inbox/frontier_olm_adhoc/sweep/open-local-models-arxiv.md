### 1. arXiv 2610.09163 - ToolRACER: A Robust Agentic Conversation Emulation Resource for Agent Training and Evaluation
- URL: https://arxiv.org/html/2610.09163v1 (v1 2026-10-06; read full HTML end to end this session)
- Quote: "native function calling models like xLAM2-3b-fc fail massively in action accuracy during Impossible conversations"
- Facts: 5.6K validated multi-turn trajectories, ~66 pct failure-prone (train 3,762 / test 1,881; six domains, 72 tools, 55 personas; Happy/Unhappy/Impossible near thirds). Pipeline = multi-agent simulation (assistant, user, and tool agents with distinct conversation views) + four LLM judges (syntax, faithfulness, role confusion, task success) + a refinement loop (only 26.3 pct of simulations pass validation first try; refinement recovers 65.4 pct, max two retries). LoRA rank 32 on Qwen3-4B: tau2-bench macro 32.20 base -> 39.20 ToolRACERBench-Train -> 41.25 combined with APIGen-MT (Retail pass@1 52.5 pct); BFCL v3 relevance/hallucination 100.00; turn-level Tool F1 91.3 (Happy) vs 62.1 for the APIGen-MT checkpoint. ACEBench out-of-domain: EA improves (Qwen3-4B 8.4 -> 10.0; Qwen2.5-32B 19.2 -> 25.0) but PA drops on multi-turn (Qwen3-4B 29.2 -> 19.0), "showing the need for improvement on long-horizon tasks (requiring >6 turns)". Runtime/hardware for evaluation not reported.
- Why it matters (RQ1): the strongest published answer this window to "can the 1-8B class sustain multi-step tool loops": yes after targeted fine-tuning, with two hard edges the estate must plan around: (a) native function-calling small models collapse on system-originated failures (backend failure, empty results, timeout, policy constraint), which is exactly the janitor lane's real environment; (b) the wall is long-horizon (>6 turns), where process accuracy regresses even after training. The 66-pct-adversarial data recipe (inject user- and tool-originated adversity, judge, refine) is a steal for any estate attempt to train the janitor tier for robust loops.

### 3. arXiv 2609.21704 - SpecQuant: Speculative Decoding with Multi-Parent Quantization for Adaptive LLM Inference
- URL: https://arxiv.org/html/2609.21704v1 (v1 2026-09-18; read full HTML end to end this session)
- Quote: "a training-free framework, that combines speculative decoding with multi-parent quantization"
- Facts: the model's own quantized variants (INT4, FP8, FP16) act as draft models for the full-precision parent; because draft and parent share weights, "their token distributions differ less during decoding" so acceptance is high. Qwen2.5-7B-Instruct measured: MMLU 4.07s -> 3.01s (35.2 pct, accuracy 72.5 -> 72.3, acceptance 66.1 pct), AlpacaEval 42.6 pct (acceptance 60.9 pct), GSM8K 37.3 pct (acceptance 57.9 pct); average latency reduction 38.4 pct at under 2 pct accuracy drop. A prompt-complexity estimator (length, syntactic complexity, named-entity density) routes: low -> Q4, moderate -> Q8, high -> FP16 direct; measured prompt mix 28/52/20 pct, so 80 pct of prompts decode speculatively. Training-free. Has a CPU-only fallback mode (both models in system RAM) and a hybrid mode (draft on CPU when VRAM is constrained). No GPU/CPU model names or hardware specs reported; llama.cpp and GGUF never mentioned.
- Why it matters (RQ1 tokens/s on the RDNA1 box): the estate's named unswept gap (speculative decoding, corpus.md:56) has its cheapest answer shape here: draft with a Q4 GGUF of the SAME model and verify with the Q6/Q8 artifact (llama.cpp draft-file pattern), which lifts tokens/s without a second model's memory bill and without any FP8 path.
