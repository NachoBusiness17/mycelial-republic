SPEC FIRST:
- No doc pinned the write semantics, so roblox/README.md (owner of the ShadowLedger behavior description, bullet at :64-66) was updated BEFORE the code: durable write law (t74) = every append goes through one UpdateAsync on the player+day key so concurrent records from multiple servers serialize and no row is lost; stored value stays a plain array of entry rows so saves written before the law read back unchanged. ROOT CAUSE (read before edit):
- record() :40-51 spawned one task per entry: :43-45 GetAsync(key), :46-47 append, :48-50 SetAsync(key, rows). Two tasks or two servers interleaving read-then-write on the same player+day key: the later SetAsync clobbers the other's append. Official docs (create.roblox.com/docs/en-us/reference/engine/classes/GlobalDataStore.md, fetched 2026-09-25): SetAsync "may cause data inconsistency if two servers attempt to set the same key"; UpdateAsync is "safer for handling multi-server attempts".

FIX SHAPE (after edit, ShadowLedger.luau :40-69, file 75 -> 89 lines):
- :58-67 pcall(store:UpdateAsync(key, transform)). Transform :59-66 copies old rows into a fresh table then appends entry: side-effect free, never yields.
- Copy-then-append (not mutate-and-return) is load-bearing: the docs say the transform "will be called as many times as needed" with prior results discarded and "cannot yield"; a mutating transform could double-append on a retry.
- Docs also say a nil return cancels the write; not used here (transform never returns nil).
- Key format unchanged (:42 "p%s_day%s", player id + UTC YYYYMMDD); store name unchanged (:13 "ShadowLedger_v1").
- Receipt comment :43-57 cites t63.next_steal, the doc quotes, the retry law, the schema, and the no-batch decision.
