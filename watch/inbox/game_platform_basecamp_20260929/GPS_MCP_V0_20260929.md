## What built (self-contained package, tools/gps_mcp/)

- `tools/gps_mcp/ledger.py` - SQLite capability ledger. Schema exactly
  as specced: `capability(model_id, task_shape, pass_rate,
  sample_size, cost_usd_per_call, last_measured, updated_at, PRIMARY
  KEY(model_id, task_shape))`. `record_verdict()` updates pass-rate as
  an incremental running mean (never overwrites history with one
  observation); `report_capability()` reads. Added one audit side
  table `verdict_log(ts, model_id, task_shape, verdict,
  evidence_hash)` so evidence hashes are retained without touching the
  required capability schema.
- `tools/gps_mcp/router.py` - `ask()` and `cascade()`. Priority order
  exactly as specced: (a) hard constraints (max_cost_usd,
  max_latency_ms), (b) ledger pass-rate (default threshold 0.85,
  caller-overridable), (c) cost, (d) endpoint's calibrated confidence
  (recorded on asks; the escalation trigger in cascade). Exploration
  rule: no ledger history for the task shape routes to the designated
  mid tier with `exploration: true`. Cascade: cheapest qualifying tier
  first, escalate one tier when returned confidence is below the
  caller threshold (default 0.8), max 3 tiers, prior answer attached
  as context, full trace returned. Every decision (including no-route
  and every cascade attempt) appends one JSONL receipt row
  `{ts, task_shape, chosen, considered, reasons, cost_usd, confidence,
  exploration}` (cascade rows add trace_id + cascade_step).
- `tools/gps_mcp/providers.py` - one JSON/YAML config for all
  endpoints (base_url, model, tier, cost_usd_per_call, latency_ms,
  test_double, confidence knobs). TEST-DOUBLE mode: in-process fake,
  deterministic canned answers derived from sha256 of the payload (no
  RNG anywhere), configurable confidence per model and per
  task_shape, latency declared (constraint-checked) not slept. Real
  mode: stdlib-urllib OpenAI-compatible POST {base_url}/chat/completions.
- `tools/gps_mcp/server.py` - stdlib JSON-RPC 2.0 stdin/stdout loop
  exposing MCP-shaped tools/call for ask, cascade,
  report_capability, record_verdict; MCP mapping documented in the
  README so real-MCP wiring later is mechanical.
- `tools/gps_mcp/seed_fixtures.py` - seeds 6 synthetic models x 5 task
  shapes (30 rows) with hand-picked varied plausible rates (tiny
  models shine on yes/no, collapse on design judgment; frontier wins
  all at 30x the price). Idempotent, deterministic literals.
- `tools/gps_mcp/config.json` - shipped all-test-double config, $0
  offline out of the box.
- `tools/gps_mcp/test_gps_mcp.py` - the suite. `tools/gps_mcp/README.md`
  - run instructions, real-endpoint pointing (LiteLLM/Ollama/OpenAI-compatible),
  honest not-doing section, IF WE GROW THIS ranked 3.

## Design decisions (the ones that matter)

1. Test doubles live behind the same call boundary as real providers
   (`call_provider` dispatch), never inside the router. This makes a
   double indistinguishable from a live endpoint to every layer above,
   which is what makes the $0 claim and the tests honest; the router
   has zero test-only branches.
2. Receipts are per decision step, not per request: one ask writes one
   row, a 3-tier cascade writes three rows sharing a trace_id. A
   cascade summary row would hide per-tier costs; the step rows make
   "which tiers tried, why, what each cost" auditable line by line,
   and the append-only test proves earlier rows stay byte-identical.
3. Verdicts are separated from prices: record_verdict updates truth
   (running mean + evidence hash into the audit table) and never
   writes cost; constraint filtering uses the live config price, the
   ledger's cost column is the last measured cost. Truth and price
   change on different clocks; conflating them invites routing off
   stale prices.
4. (Flagged deviation) The build-lane mission named three server
   tools; the BUILD section of the spec defines four (cascade is tool
   4). Followed the spec: four tools exposed. Trivial to hide cascade
   if the operator wants the narrower surface.

## What the Opus spec-review should critique first

1. The escalation policy boundary: cascade escalates on ONE bit
   (calibrated confidence < threshold) with a hard 3-tier cap. Is
   confidence the right trigger, at the right strictness, or should
   escalation weigh (confidence, cost-so-far, remaining budget)
   jointly? This is the decision boundary the amendment says the
   frontier should own.
2. The ledger trust model: record_verdict accepts any caller's verdict
   with an unverified evidence_hash. Nothing binds a verdict to a
   checkable artifact, so pass-rates are trivially inflatable; the
   verification-gate contract (IF WE GROW THIS item 1) is where the
   spec-review should push hardest.
3. Threshold greed vs drift: fixed 0.85 pass-rate gate with no time
   decay means yesterday's 0.9 routes today's traffic. The review
   should decide whether v0 ships with decay/bandit semantics or the
   greedy gate is honest enough for a prototype (and when stale
   measurements must force exploration).
