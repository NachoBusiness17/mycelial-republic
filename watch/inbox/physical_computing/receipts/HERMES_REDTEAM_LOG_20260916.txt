**Attack 1 — Fleet-as-thermodynamic-sampler analogy**

The analogy assumes each lane is a Markov state with detailed balance and a stationary distribution over "judgment." But salon lanes are deterministic function evaluations with different inductive biases, not stochastic draws from a Boltzmann machine. There is no transition kernel, no temperature parameter, no proof of irreducibility or aperiodicity. "Inter-lane decorrelation" measures output divergence, not mixing: two lanes can diverge while both converging to the same wrong answer, or converge while appearing distant. ESS requires a well-defined target distribution — the pack never defines the distribution over "quality" that the fleet would be sampling. The analogy is load-bearing and false: it conflates diversity with decorrelation and decorrelation with mixing.

**Experiment 1 (zero cost):** Take 50 existing salon_50 receipts. Embed lane outputs, compute pairwise distance matrix. Correlate inter-lane distance against human-judged quality on a held-out 20-receipt subset. If ρ < 0.3, the analogy dies.

**Attack 2 — Mycelium instrumented-cube program**

"Reservoir computing on mycelium" is folklore without the engineering specs. Reservoir computing requires a fixed high-dimensional dynamical system with separation of timescales, fading memory, and the echo state property — none of which the pack demonstrates for fungal substrate. The proposed "readout beats chance" test is vacuous: any noisy analog system (a photodiode, a thermometer) beats chance on a trivial pre-registered task. The pack specifies no substrate preparation, no controlled variables, no Lyapunov/ES characterization, and no baseline against random noise. A $200 budget buys sensors and spores, not a characterized reservoir.

**Experiment 2 (~$50):** Grow one cube. Instrument with 3 Arduino sensors. Run a binary discrimination task (classify two input patterns from sensor streams) with pre-registered n=100, α=0.05. If readout doesn't beat chance, it's an altar, not a computer.

**Attack 3 — DAD discipline on sim stones**

DAD is unfalsifiable as written because "verify" is circular: the physical step is verified against the digital simulation, but the simulation IS the spec. You confirm the simulation, not the physics. There is no independent ground truth. The pack's own hydraulic sim stone lives inside the MUD engine — the "physical step" is just another function call in the same codebase. "Publish encode/decode/verify overhead share" is meaningless without a reference implementation that isn't the thing under test. DAD binds only with a third verification channel the pack never provides.

**Experiment 3 (~$15):** Build the two-bucket XOR physically. Run 100 input patterns through both MUD simulation and real water logic. Compare physical output to MUD prediction. If deviation exceeds measurement noise, DAD catches real physics; if not, you've only verified the MUD.
