## Approach

DFHack answers one question per fix that our ratchet never asks of a debt row: **how may this be cured, and who has to say yes?** Their register ships the answer in the fix's mode field (`dfhack_fixes.json`, mode per entry): always-on (`quickfix.set_entity_race_references`, "automatic on load (always)", line 297), default-on periodic (`fix/dry-buckets`, "automatic (periodic, default-enabled via gui/control-panel)", line 108), opt-in (`fix/wildlife`, "NOT default: some players keep wildlife captive", line 288), manual-only (`fix/stuck-merchants`, "must not run while merchants are on-map; not repeat-safe", line 233). The FOLD already demands the transfer (`dfhack_fixes_FOLD.md` line 26): every registered debt should name "whether a gate may auto-fix it or whether auto-fix destroys signal."

This proposal stamps one of the four dials onto every row of `configs/violation_baseline.json` as a **total function of the rule name alone**, so a row can never sit in two tiers: one rule, one dial, deterministic. Ambiguity does exist, but it lives at the FILE level, not the row level, and it exists today in bytes: `tools/pupeteer_gauntlet.py` carries live claims on three dials at once (except-pass: default-on; file-too-long + shell-true: opt-in; mimosa-ssrf + mimosa-command-injection: manual-only). The tiebreak law is therefore two clauses: (a) row dial = f(rule), total, unknown or namespaced future rules default to the most restrictive dial; (b) remediation on a file takes the most restrictive dial among its live claims, precedence manual-only > opt-in > default-on > always-on. Restrictive-wins mirrors B2-95's own law that external provenance beats derivability (`tools/violation_ratchet.py` lines 10-17).

Each dial then carries exactly one delete-when-X retirement receipt condition, in DFHack's retirement shape: their six retired fixes each cite the upstream cure ("DF bug 3295 fixed upstream in DF 0.40.05", `dfhack_fixes.json` lines 454-461) plus one consolidation (three occupancy fixes merged into `fix/occupancy`, line 460). Ours cite estate commands and commits the same way. The gate itself (`check` behind `githooks/pre-push`, hook line 12) is not a dial: it is the constitution's floor, always-on by hook, carries no debt, needs no retirement condition.

### The four retirement conditions (one per dial, each names its receipt)

1. **always-on: delete-when-cold.** Fire when the dial's rules emit zero hits AND hold zero registered claims on two consecutive full-scope scans, with the commit that cured the final row named. Receipt: dated pair of `check` stdout summary lines plus the curing commit hash, filed in `watch/inbox/`. Command: `.venv/Scripts/python.exe tools/violation_ratchet.py check` (full scope, not `--changed`), run on two different days.
2. **default-on: delete-when-drained-stable.** Fire when the registered count for the dial's rules is monotonically non-increasing across 7 consecutive scheduled patrol executions and the final run shows zero registered, zero NEW. Receipt: the 7 dated patrol log lines plus the final check output. (DF shape: the occupancy consolidation, three registers merged into one rather than kept.) Today's standing count is 678 plus 5 pending, so this condition is honest, not aspirational; it fires only on real drain.
3. **opt-in: delete-when-disposed.** Fire when every row the dial holds has a named disposition: cured-via-enrolled-lane (claim left via prune after the enrolled cure landed) or re-triaged to manual-only by name; zero undisposed rows. Receipt: the disposition table (fingerprint, disposition, evidence) filed as one receipt. (DF shape: `fix/wildlife`'s enable state is a persisted per-site choice, lines 287-289; the fix retires when nobody holds it enabled.)
4. **manual-only: delete-when-re-triaged.** Fire when the last claim leaves by explicit re-triage naming the fingerprint and its settle evidence; silent or automated reap stays forbidden forever (B2-95, enforced structurally: prune keeps non-scanner-domain claims, `tools/violation_ratchet.py:315-325`). Receipt: the re-triage receipt listing every removed fingerprint plus per-claim settle evidence. (DF shape: `fix/stuck-merchants` retires only when DF bug 9593 lands upstream, cited by number; retirement is an upstream fact with a citation, never a drift. This condition may stay unfired for the estate's whole life, which is different from unfireable, and is by design.)

## Falsifier

- **Two-tier hazard, checked against bytes this session.** The partition command stamped all 933 rows with zero unstampable and zero residue (output above in session log: `{'opt-in': 197, 'default-on': 678, 'manual-only': 58} sum= 933; unstampable rows: []`). Any future row that cannot stamp, or any rule needing file-level judgment to place, kills the function-of-rule law. The real ambiguity was found at file level and is resolved by the restrictive-wins precedence with four live mixed files as proof.
- **A dial without a retirement receipt condition kills.** All four conditions above name the exact command and the exact receipt artifact; none is "eventually someone decides."
- **A retirement condition that cannot fire kills.** Manual-only's condition may stay unfired forever (operator never settles the mimosa surface); that is by design and mirrors `fix/stuck-merchants` waiting on DF bug 9593. If the panel judges an indefinitely-unfired condition as unfireable, that is the kill.
