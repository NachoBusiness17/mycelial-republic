### 2. Architecture and defense ordering

A MINTER seat samples candidate (file, span) pairs per stratum from primary
surfaces (authored files; excludes corpus/, mine/, agents/, memory/biography/
derived and residual, memory/agent_sessions, .bak paths, kind=corpus
harvested text), runs the eight screens, writes one question line per
surviving candidate WITHOUT the span or any gold path token run, then seals.
Seal split: questions + gold + salts go to C:/Users/foste/.mag_eval/uf122/
(OUTSIDE the projects walk root mag/catalog_scan.py:83 walks and outside the
repo confinement tools/corpus.py:79-98 enforces), while salted commitments
sha256(salt + canonical gold json) land in-repo at
catalog/eval/uf122_status.json (catalog/ is walker-excluded,
mag/catalog_scan.py:88; catalog/eval verified absent today,
environment_checks.txt, so no stale seal exists). A MINER (the seat or
mining pass under test) receives questions only and answers with citations
through the corpus surface. A GRADER (deterministic local script, no LLM
judge, no network) re-reads gold, verifies each cited path's live bytes
contain the span, and writes verdicts containing NO spans and NO gold paths.
The GATE: tools/uf122_eval.py check exits 0 while a current baseline exists
(scored, pinned to the current catalog map_sha256, and inside the gold-rot
caps of section 5) and exit 2 when absent, stale, map-changed, rot-capped,
or seal-without-vault. A mining pass (any change that alters what the corpus
surface returns: scanner, tags, index, ranking; or any fine-tune corpus
selection) requires check=0 to start and a post-change condition-B re-run
within the no-regression budget to ship. This mirrors the estate's
exit-2-only hard-block law (AGENTS.md build discipline, githooks/pre-push
pattern) and CONSTITUTION.md line 13 per the survivor's citation ("Mining
proposals never auto-merge"): the gate never blocks thought, only ships.

Defense ordering (named, per critique): the PER-RUN MINER BLIND ARM is the
load-bearing leakage enforcement and owns the leakage kill condition at run
time; the S8 janitor closed-book probe is a MINT-TIME TRIPWIRE only.
Rationale: the adversary that matters is the evaluated seat, and the per-run
arm measures exactly it (same seat, tools off, immediately before the armed
run), so it is the defense that carries the kill condition. gemma:2b is a 3B
local janitor (present this session, ollama_tags.json) unlikely to
blind-solve estate trivia, so its sensitivity to subtle leaks is low by
construction; its job is to catch gross leaks, a span that reached
common-knowledge surfaces. Both thresholds still kill a mint, at different
moments: S8 > 5 blind-solves kills the MINT at seal; the per-run arm > 5
blind-solves in any scored run kills the mint and forces re-mint.

### 3. The eight screens (all local, all run at mint; S1-S5 also re-runnable
at score)

S1 corpus-only: the span occurs in >= 1 file's bytes (batched full-pool
scan; measured 56.8 to 60.2 s per full pass in the minting session, ~30 MB/s,

S2 settling set, BOUNDED GROWTH: seed from the shortest distinctive token

the shorter span's files, so S shrinks monotonically). Termination budget:

audit surface (an honest floor under the 0.04 regression budget). S excludes

S5 no-question-leak: question text contains no run of >= 3 consecutive span
tokens, no gold basename, no primary path (mechanical check over the

S6 idiosyncrasy heuristic: the span contains at least one token with a
digit, or a hex run >= 8, or a hyphen-compound not present in any ext:*

S7 tool-fairness: the span lies within the first 256 KB of the gold file
(tools/corpus.py:70) and the file passes the same text sniff (no NUL in

S8 closed-book probe (TRIPWIRE; HARD MINT DEPENDENCY): all sealed questions
asked of the local ollama at 127.0.0.1:11434 with no tools; default probe

http://127.0.0.1:11434/api/tags connection refused; probe model gemma:2b;
no screen skipped, nothing sealed"). The status file is untouched on any
exit 2, so no baseline can ever exist on an unscreened mint; an ollama
outage produces a blocked mint, never a partial one. A substitute probe
model is allowed only by explicit flag and is recorded in the seal audit.

Per-run blind arm (RUNTIME; LOAD-BEARING): at every scored run the MINER
ITSELF runs a closed-book arm first (same seat, tools off); any question it
answers span-correct blind is retired from that run's denominator, and more
than 5 blind-solves in one run kills the mint and forces re-mint. The eval
therefore only ever scores questions the evaluated seat cannot answer
without the corpus, per run, against the actual adversary.

### 5. Gold-rot policy

Problem, verified this session: catalog ids are trivially invertible
in-repo. tools/corpus.py:101-102 derives the id as sha256(relative path)
first 12 hex, and every catalog.jsonl row carries id and path together
(first row read this session: id a54ff182c7e8, path AGENTS.md,
catalog_row_sample.txt). Any published per-question verdict carrying a cited
catalog id therefore hands a later miner the gold path, and every condition-B
re-run after the first baseline would evaluate a miner that can read prior
gold paths. Policy, three clauses plus an audit:

1. Aggregate-only until the window opens: in-repo status and watch/inbox
   receipts publish run-level aggregates ONLY (citation_recall per arm,
   denominator, retired_blind, drift_count, engine_mix, questions_rev,
   map_sha256, run counter). Per-question verdict rows (question id, cited
   ids, span checks) live vault-side; the operator reads detail in the vault
   or at window-open.
2. Window-open burns the mint: publishing gold + salts (the operator command
   that opens the post-run verification window, letting anyone recompute
   sha256(salt + gold) against pre-run commitments and replay verdicts)
   simultaneously invalidates questions_rev. Inversion can then only look
   backwards at an already-burned mint; the next scored run requires a fresh
   mint (new salts, fresh candidate draw).
3. Cadence caps even window-closed: a mint is valid for at most 10 scored
   runs and at most 30 days, whichever hits first; the map_sha256 pin
   already forces re-mint on any map change (check exit 2 map-changed).
   Over-cap mints read as stale to check and force re-mint.
4. Rot falsifier, run after EVERY scored run: grep the repo working tree and
   catalog/eval for every settling-set catalog id and span; ANY hit is rot,
   kills the mint, forces re-mint, and opens a leak investigation (how an id
   or span reached a readable surface). The one known accident class stays
   as the minting session wrote it: an operator pasting gold into the repo.

### 6. Metrics and bars

Primary: citation_recall = (answers citing >= 1 settling-set file whose live
bytes the grader re-verified contain the span) / (scored questions after
per-run blind retirement). Secondary: answer_correctness = normalized span
present in the answer text; correctness WITHOUT citation flags blind-suspect
and feeds the retirement rule. Drifted questions (gold file sha256 at mint
differs from sha256 at score) leave the denominator and are reported as
drift_count (the C6 honesty made mechanical; the minting session verified
tests/test_catalog_tags.py has 0 rows in the 2026-09-26T19:16:46Z snapshot
while existing on disk). Engine attribution: each condition-B search records
engine (fts5 vs scan) because B2-22 measured FTS5 missing mid-token hits
(tools/corpus.py:22-27 parity note, read this session); a mining pass that
flips engines changes recall and must say so. Baseline = both arms scored at
mint window; condition B re-run per mining pass; delta B minus A on citation
recall is the claim under test. A sits near 0 by construction, so its real
job is the leakage tripwire.
