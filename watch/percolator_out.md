>PLAN SUMMARY
>1. Freeze the semantics: one accepted event gets one immutable identity, one committed order position, one predecessor commitment, and one durable publication point.
>2. Serialize the allocation boundary. A concurrent writer may read optimistically, but it must validate the tail it read and lose cleanly if the tail changed. Same seq, same nonce, or same event id is a rejected conflict, not a warning.
>3. Make crash recovery a first-class state. The accepted prefix must survive a torn append; an incomplete suffix must be quarantined or truncated to the last valid record. The derived INDEX is a cache and may be rebuilt, but the event commit must be durable first.
>4. Separate tamper evidence from append mechanics. Store event_id, seq, writer, nonce, payload_hash, prev_root, and record_hash; publish a signed or externally retained tip. Verify the whole chain and the tip, not merely a root recomputed from the bytes currently in front of you.
>5. Keep the Verkle rung honest. A linear hash fold is a useful prototype and a history spine; it is not yet a Verkle tree. Only move to a vector/polynomial commitment when the state vector, witness format, update cost, setup assumptions, and verifier contract are written and tested.
>
>WHAT THE BIBLIOGRAPHY CHANGES
>
>Lamport’s 1978 paper gives the first clean boundary: physical timestamps do not define distributed truth; the useful relation is the causal “happened-before” order, with logical clocks supplying an order compatible with it. That directly punctures the current `seq`/`ts` fallback: a timestamp tie-break is presentation policy, not a concurrency protocol. Use a single allocator, a compare-and-swap tail, or an explicit logical clock with conflict validation. Source: https://www.microsoft.com/en-us/research/publication/time-clocks-ordering-events-distributed-system/
>
>Kung and Robinson’s 1981 optimistic-concurrency paper supplies the practical shape for a low-contention fleet: read privately, validate against the shared state, then copy back atomically; abort and retry when validation fails. That is a better description of a safe append than “O_APPEND means the race is gone.” The two tools can stay optimistic, but the validation/write phase must be one serialization point. Source: https://db.cs.cmu.edu/papers/1981/kung-tods1981.pdf
>
>Schneier and Kelsey’s secure-log work makes the threat model honest. A secure log does not magically prevent a compromised logger from destroying data; it makes earlier entries difficult to alter or destroy without detection, using cryptographic chaining and key evolution/audit discipline. The missing actor in the current tools is the auditor holding a prior commitment. A tip printed by the same mutable process is not an anchor. Source: https://www.usenix.org/conference/7th-usenix-security-symposium/cryptographic-support-secure-logs-untrusted-machines
>
>Crosby and Wallach’s 2009 history-tree paper sharpens the distinction between a plain hash chain and a tamper-evident history. Their system commits successive versions, proves that old and new views are consistent, and supports membership proofs without handing the auditor the whole log. A linear chain is fine for a small local log, but its proof path grows with the prefix; a history tree gives logarithmic proofs and, crucially, makes cross-version consistency an explicit operation. Source: https://www.usenix.org/conference/usenixsecurity09/technical-sessions/presentation/efficient-data-structures-tamper-evident
>
>RFC 9162, Certificate Transparency v2, is the most operationally useful template. It requires an append-only Merkle log, allocates a tree index, produces a root, signs a tree head, and lets monitors check inclusion and consistency between old and new tree heads. The lesson for Mag is not “become a public PKI”; it is “retain a prior tip, publish it outside the mutable log, and test both inclusion and extension.” A tail proof without a trusted tree head is only a local recomputation. Source: https://datatracker.ietf.org/doc/html/rfc9162
>
>SQLite’s atomic-commit and WAL documentation gives the crash-consistency counterweight. Atomicity is an on-disk protocol, not a property inferred from a successful function return. Journaling, ordering, sync boundaries, and recovery determine whether a restart sees the old state, the new state, or a corrupt mixture. The research literature confirms the uncomfortable part: application-level crash protocols depend on filesystem persistence behavior and can fail in small, surprising workloads. If this board remains JSONL, implement and crash-test the equivalent protocol; if the priority is shipping correctness, a small SQLite WAL ledger is a credible substrate for event allocation and derived views. Sources: https://www.sqlite.org/atomiccommit.html · https://sqlite.org/wal.html · https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai
>
>Node’s current fs documentation says `appendFileSync` defaults to `flush: false`. Linux’s `open(2)` documentation says O_APPEND makes offset selection and the write one atomic step, but explicitly warns that concurrent append can corrupt files on NFS. Both facts support the narrow claim only: append mode helps with the byte-position race on some local filesystems. It does not allocate unique sequence numbers, validate a predecessor root, provide power-loss durability, or make a JSON line semantically idempotent. Sources: https://nodejs.org/api/fs.html · https://linuxman7.org/linux/man-pages/man2/openat.2.html
>
>KZG10 explains why polynomial commitments are attractive: a committer can bind a polynomial with a short commitment and open evaluations with constant communication. That is a cryptographic commitment primitive, not a concurrency protocol and not a crash journal. It comes with field/group assumptions and setup choices. Ethereum’s Verkle explanation shows the system-level reason for the machinery: vector/polynomial commitments can make witnesses much smaller than sibling-heavy Merkle proofs, helping stateless validation. Therefore the project should not call the current linear root “Verkle”; first make the event ledger correct, then specify whether the future commitment covers a sequence, a key/value state, or both. Sources: https://www.iacr.org/archive/asiacrypt2010/6477178/6477178.pdf · https://ethereum.org/roadmap/verkle-trees/
>
